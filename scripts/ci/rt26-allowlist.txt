# RT-26 allowlist registry — ONE V1 service_role surface per ADR-016 Decision 4.
#
# Each non-comment, non-blank line is a permitted file path (relative to repo root).
# References to SUPABASE_SERVICE_ROLE_KEY in any other file within audit scope
# (api/src/** + repo-root config files) trip the fence at PR-time (fail-closed).
#
# PATH SHAPE (per SELF-181 RT-26 fence-path fix, 2026-07-02):
#   The SvelteKit app is scaffolded under api/ (SELF-185), so audit scope is
#   api/src/ and entries carry the api/ prefix. The fence does EXACT-STRING path
#   matching against grep's emitted path (api/src/routes/...); the api/ prefix is
#   load-bearing — without it a legitimate surface would TRIP the fence when it
#   lands. Pre-SELF-185 these were src/routes/... (repo-root scaffold).
#
# WHY THIS REGISTRY IS ONE LINE (ADR-016 Decision 4, 2026-08-10).
#   It permitted four paths until then. Three were removed: two named routes that
#   DO NOT EXIST (`onboard/`, `revoke/`), and the Plaid `webhook/` route, which
#   exists and holds ZERO service_role references — its own header asserts the
#   factory is the sole RT-26 surface. Decision 3's delegate-to-worker model
#   superseded all three and the registry never followed.
#
#   ⚠ THIS WAS A FAIL-OPEN DEFECT, NOT UNTIDINESS — and it is the reason to keep
#   this file short. The fence does exact-string matching of grep hits against
#   these lines. It NEVER validated that an entry corresponds to an existing file,
#   so a stale entry was invisible to CI and cost nothing UNTIL a file appeared at
#   that path — at which point the fence SILENTLY PERMITTED it. Each stale line was
#   a standing pre-authorization to bypass the factory discipline Decision 3
#   ratifies, at exactly the paths where Decision 3 says raw references must not
#   exist. (That hole is now closed at BOTH levels. The fence validates that every
#   entry names a file that EXISTS and that actually REFERENCES the key — see
#   `fence-rt26-service-role-allowlist.sh`. Existence alone was not enough: it
#   catches `onboard/` and `revoke/` but NOT `webhook/`, which existed while holding
#   no key. Both checks together catch all three, in a single pass.
#
#   ⚠ WITH A SINGLE ENTRY, USE-VALIDATION IS A TRIPWIRE ON THE FACTORY ITSELF. If
#   supabase-admin.ts ever stops referencing the key, CI goes red — and THE FIX IS
#   TO REMOVE THIS ENTRY, never to re-add a key to satisfy the check. A surface that
#   stopped needing service_role is good news; the registry shrinks to match it.
#
#   ⚠ TEMPO CONSTRAINT this introduces on ADR-016 D2. D2 gates changes at "the
#   surface-introducing lock"; an entry could previously be ratified and land BEFORE
#   its code. It cannot now — an entry whose file does not yet reference the key
#   fails CI. The entry must land in the SAME change as the key-referencing code, or
#   after it, never before. D2's gate is unchanged in substance; only the ORDER is
#   constrained. Flagged to Architect as possibly worth an ADR-016 note; ADR
#   authorship is not DevOps's to perform.)
#
#   The route that actually implements the old entry-2 surface is
#   `api/src/routes/api/plaid/exchange/+server.ts`, whose header reads: "This route
#   holds NO Plaid secret and NO service_role key → stays OFF the RT-26 allowlist."
#   It declines the permit by design. That is the pattern; keep it.
#
# ⚠ THE OBLIGATIONS SURVIVE THE PERMITS. Decision 1's three-surface commitment
#   stands in full. The SD-03 credential-class admission and retention obligations
#   live in Decision 1 and in SECURITY §4.2 + §4.6 — NOT in this grep registry — and
#   the unbuilt `/item/remove` bounded-Item-active-only retention commitment survives
#   the removal of its permit intact. A permit says where a raw key MAY appear; an
#   obligation says what V1 MUST do. Removing the first does not touch the second.
#
# Lock anchors:
#   - ADR-016 Decision 4 (the prune to one entry; canonical composition).
#   - ADR-016 Decision 3 (delegate-to-worker model + one-audited-key-home factory).
#   - ADR-016 Decision 1 (the original three-surface enumeration + the SD-03
#     obligations, which this prune does not touch).
#   - ADR-016 Decision 2 (webhook-allowlist annotation convention).
#   - SECURITY §4.2 axis vi (V1-SHIP-BLOCK + HIGH severity posture obligation).
#   - ARCH §4.1 (RT-26 allowlist anchor narrative).
#   - ADR-011 Decision 4 (second catalogued §10 instance).
#
# CHANGE POLICY (per ADR-016 D2, scope fixed by D4):
#   ANY change to this composition — addition OR removal — requires Sec-consult +
#   an ADR-016 amendment. D2's wording is addition-shaped because additions were the
#   only case that had arisen; D4 is the precedent establishing that a REMOVAL takes
#   the same gate, because the ratified object is the composition and shrinking it
#   changes that object exactly as growing it does. A prune is not editorial.
#   This file is NOT freely editable; updates land alongside the amendment PR.
#
# ADDING A SECOND ENTRY — the answer is almost certainly "don't". Per Decision 3 the
#   factory is deliberately one audited key-home: future service_role surfaces
#   REUSE `supabaseAdmin()` rather than adding entries, and callers hold no key.
#   A new surface that genuinely cannot use the factory is an ADR-amendment
#   one-way-door — route to Architect, not an inline addition here.
