## §5 framing — capabilities on the eventual trajectory

§5 is the consolidation home for the V2+ deferred capabilities surfaced across the V1 PRD lifecycle — every V1/V2 boundary clause in PRD §2.1 → §2.6 and the deferral surfaces created by the relevant ADRs (ADR-002 Finding (b); ADR-004 Decisions A–D; ADR-005; ADR-006; ADR-007). The §5/§6 axis is sharp: §5 enumerates capabilities that **are** on the eventual product trajectory — locked-as-V2+ in V1 to preserve the single-user drop-replace-migration scope but anticipated as legitimate later work; §6 enumerates capabilities that are **not** in this PRD's universe at all (see PRD §6 for the full axis enumeration — five permanent product-identity axes per ADR-002 §3.0 + ADR-007). "Later" vs "not in this PRD's universe" is the operative distinction. §5 is to *capabilities* what §3.5 is to *measurement frames* — both make the V1 perimeter visible by its complement and prevent re-litigation of settled scope decisions. §5 introduces no new V2+ items; every entry traces to an existing §2.x V1/V2 clause or an ADR-locked deferral.

## §5.1 — Net-worth deferrals

- **User-configurable time-axis controls on NAV surfaces.** V1 fixes the §2.1.2 NAV-over-time rolling window (60 months), the §2.1.3 multi-horizon NAV-delta horizon set (Month / YTD / 1-Yr / 3-Yr / 5-Yr), and the §2.1.4 NAV-at-reference-dates set (This Month / Prior Month / Prior Year-End). User-configuration of any of these three V1-fixed sets is V2+ per the §2.1.2 / §2.1.3 / §2.1.4 V1/V2 clauses. Deferral rationale: V1 calibrates against the existing-system Finance_Report fixed shape for parity-grounded migration; configurability is post-parity-soak expansion.
- **Per-scope NAV reporting + scope-aware UI filtering.** §2.1.7 V1/V2 (ADR-004 Decision B). V1 data model carries scope on every account from V1 bootstrap so the V2 expansion ships without a data migration; V1 UI is full-household-only. Per-scope NAV views, per-scope NAV-over-time charts, and scope-filtering affordances on §2.1 surfaces are V2+.
- **Per-tenant CPI-U source override.** V1 settles on a single CPI-U sourcing decision per Architect Phase 3 routing flag at §2.1 (live API vs. user-managed seed); per-tenant override that lets the user choose between CPI-U sources or supply a custom inflation series is V2+. Deferral rationale: single-user V1 has no use case for per-tenant CPI-U divergence; V2+ multi-user expansion may surface it.
- **Historical NAV import beyond V1 Dec-2015-forward parity import.** V1 imports the F/CTO's existing Google Sheet monthly NAV history from Dec-2015 forward as the parity baseline (§2.1.3 trace; Architect routing flag at §2.1 for the import mechanism). User-facing historical NAV import surfaces beyond this V1 parity import (bulk CSV import of NAV history for new tenants in V2; user-driven historical correction workflows) are V2+.
- **Per-month carry attribution on inflation-adjusted figures.** V1's [ADR-049](DECISIONS.md#adr-049) Decision 5 marker states *that* a figure's span includes a carried CPI-U month; it does not attribute *which* months were carried. V2 candidate: per-month hover attribution. **Named and deferred at the 2026-08-10 product ruling ((a) + Option B), not overlooked.**
- **Reference-series health status view.** A surface mirroring §2.4.4's connection-state view, but for reference series (CPI-U) rather than accounts. **Deferred at the same ruling on an explicit basis: one real gap, zero built consumers — a status surface is unwarranted at V1 scale.** Revisit if the gap count grows or a second reference series lands.
- **⚠ User-selectable gap policy (carry-forward vs interpolate vs suppress) — NEVER IN V1, and this entry is a NO, not a QUEUE.** Filed in §5 so the decision is findable, but it is **not a V2 candidate awaiting capacity**: interpolation **changes a financial calculation**, so it routes to Architect + Sec as a decision, not to PM as scope. ⚠ **Suppression was named and rejected on its merits** — it blanks the §2.1.3 / §2.1.4 headline scalars and punches a hole in a 60-month chart over a publication lag; a marked carry-forward is strictly better information. **Do not promote this to V2 by reading the section header.**
- **⚠ NOT a §5 entry, recorded here only so its absence is not read as an omission: gap detection / alerting.** This is **Architect's**, under [ADR-049](DECISIONS.md#adr-049) Decision 3's lag rule — not a deferred product capability. ⚠ Related and open: **[`BACKLOG.md`](BACKLOG.md) §7.6 S22** — stalled-ingest detection currently has **no owner anywhere**, and the shipped helper explicitly declines the job.

## §5.2 — Allocation deferrals

Whether V1's allocation-view layer supports drill-down as a general capability (any Sub-Cat → own sub-rows) versus hardcoded US Equity special case is Architect Phase 3; user-extensible drill-down is V2+ regardless.

It is *correct with respect to the ledger* and *may be surprising with respect to the viewer's wall clock*: a close at 18:00 Pacific renders as the following day. **Only the second is true, and the difference is load-bearing** — *"we accept a wrong date for all of V1 on a fintech app"* invites rejection on the strength of a description nobody checked, while *"we accept a date that may read a day later than your wall clock, because it is the date the system actually reasoned with"* is the same decision and the defensible one. **It is not a rendering bug to be swept.** The three closure surfaces — accounts hub, account detail, connections — agreeing *is the property protecting them*: `059`'s `closed_at` column comment pins that `closed_at::date` evaluates in the session TimeZone, and what makes it safe today is that the as-of date is **server-derived**, putting the gate and the display on one clock. Switching the display side to local — on one surface or coordinated across all three — re-opens exactly the off-by-one-day that comment measures, and does so *silently*, which is why the coordinated sweep is the worse of the two wrong moves. **What is deferred is the capability, not the fix:** rendering dates in the user's own zone requires resolving the tenant-timezone question `059` explicitly assigns to *"whoever makes `p_as_of` user-supplied"* — where a tenant's zone is stored, and which clock the as-of gate then reasons on. ⚠ **DO NOT READ THIS AS INDEFINITELY DEFERRED — the trigger is one feature away, and `059` says so in its own words.** The `closed_at` column comment, verbatim: *"**THAT DEPENDENCY IS NARROWING, NOT STABLE:** `059` **STRUCK** the ADR-039 sound-only-at-`current_date` constraint and thereby **LEGALISED past as-of dates**, so a **§2.1.2 trajectory passing a USER-CHOSEN date is now a sanctioned path** — and the first caller that supplies `p_as_of` from a user's calendar rather than the server's breaks the agreement, **silently**, in the user's favour or against it depending on which side of midnight they closed."* **Whoever picks this up may be the trigger rather than someone waiting for it.** ⚠ **And the consequence is NOT the cosmetic one this entry opens with.** The display half is a wall-clock surprise; **the as-of half is an inclusion difference on a net-worth read** — `059` measures it: *a user in UTC−5 closing at 20:00 local on Mar 1 records `2026-03-02 01:00Z`; under session TimeZone UTC that is `closed_at::date` = Mar 2 and the account is **INCLUDED** at `p_as_of` = Mar 1, while under session −05 it is Mar 1 and **EXCLUDED**.* Same account, same instant, two different net-worth answers, chosen by a session default nobody set deliberately. **That is a financial-correctness hazard, not a formatting one, and it is currently held by a comment rather than a constraint** — see the `apply-migration` / `spawn-sec-joint-review` checkpoint *prefer a declarative constraint over a comment asserting an invariant*. **Sec view requested on whether the comment is sufficient control here;** flagged by PM, not adjudicated by PM. **V2+:**
  - **Per-tenant timezone attribute** (storage + selection surface). **The blocker is not "we haven't done timezones yet"** — it is specifically that the tenant's zone must be **stored or threaded**, never left to the session default to decide.
  - **As-of evaluation re-pointed onto the tenant zone**, so gate and display stay on one clock rather than diverging.
  - **Date rendering in the tenant zone** across every surface that displays a dated bookkeeping fact, swept together rather than per-surface. **Sequencing, and it is the whole point of the entry: land the display change WITH the tenant-zone work, never before it.** Shipping the render first is the silent flip this entry exists to prevent.
  - *Why this is booked rather than left in the ADR: the ADR answers **"why is this UTC?"** for whoever asks. It does not answer **"when do we get local dates?"** — and the flag has now been raised twice, which is the signal it will be raised a third time. Two artifacts, two jobs.*

  - **`pfin.eod_price`** — `019`'s `eod_price_select` is **asset-anchored** (`exists (select 1 from pfin.asset a where a.asset_id = eod_price.asset_id and (a.users_id is null or a.users_id = auth.uid()))`) and the table carries **per-user `manual_valuation` rows**, with INSERT / UPDATE / DELETE each gated on `source = 'manual_valuation'` **and** `a.users_id = auth.uid()`. Under `service_role`, `select * from pfin.eod_price` returns **every tenant's manually-entered valuations — user-entered money figures — overwritable by the same mechanism.**

- **The hazard in one line.** Under `service_role` the read pulls **every tenant's private rows** into worker memory, **and the read is the smaller half**: `update_table_df` bulk-UPDATEs from that frame, so an FMP profile refresh could silently overwrite another tenant's private row. **Widening the read role to fix a permissions defect would have manufactured a cross-tenant WRITE hazard** — fixing a fail-closed bug by failing open, one layer down. **RULING: reads `authenticated`, writes `service_role`.** `authenticated` with no JWT is not degraded — it resolves to exactly the global partition wanted, fail-closed, with no SQL change.
- **Grounding, so this does not read as an empirical finding about two tables' shapes.** [ADR-011](DECISIONS.md#adr-011) Decision 1 clause (b) says ***"Writes* execute under `service_role`"** and is **silent on reads**. Reading it as *"the privileged context runs as `service_role`"* is **the widening that produced the hazard** — the table shapes are where it surfaced, not why it was wrong. *(Carried canonically by the ADR-023 amendment; the redundancy here is deliberate.)*
- **✅ Two BLOCKING test controls (Sec), beyond the legs already specified.** **(i)** Assert SQLSTATE **`42501` by code** — not by message text, not by "it raised" — on **both** the read and write legs, against tables that exist. ⚠ **Scoped to `fetch_table_df` / `upsert_table_df` against real tables, and NOT to "any statement" — do not narrow or tidy this without re-deriving why.** TEMP comes from **`PUBLIC` at the database level** and is granted by no migration, so **TEMP DDL succeeds privilege-less**. A proof statement that happens to be TEMP DDL **will not observe `42501`** — it will succeed, and **a RED that never appears reads as a fix that already works.** **(ii)** A **per-table read-set parity check**, with the criterion stated so it does not have to be re-derived from the rationale: **for each table the fix touches, in the same run — `count(*) as service_role` − `count(*) as authenticated` **==** `count(*) matching that table's user-partition predicate`** (**0** for a pure-global table).

It is **asset-anchored**, so its partition predicate is `exists (select 1 from pfin.asset a where a.asset_id = eod_price.asset_id and a.users_id is not null)`. **A criterion written as a bare `users_id is not null` is INEXPRESSIBLE on `eod_price`** — the very table Drift 1 added to this veto for holding user-entered money. Instantiations: `asset` → `users_id is not null`; `eod_price` → the asset-anchored EXISTS above; `cpi_u_index` → pure-global, expected delta **0**.
  - **📐 HOW TO INSTANTIATE IT — the mechanical rule, which is the reusable part.** ***Take the table's SELECT policy's `USING` clause, set `auth.uid()` to NULL, and negate what remains.*** Worked on `eod_price`: `eod_price_select` is `exists (… a.users_id is null **or** a.users_id = auth.uid())`; with `auth.uid()` NULL the visible set collapses to `exists (… a.users_id is null)`; the delta is its **complement**, `exists (… a.users_id is not null)`. **Derived from the policy, not intuited from the table.** ⚠ **Stated because *"write that table's user-partition predicate"* on its own re-opens the exact authoring risk that produced both of this section's compose-failures** — an author instantiating from their mental model of the table. The rule above is **checkable by a reviewer**; "write the tenant predicate" is not.
  - **🎯 The property the criterion serves**, so a new table's instantiation can be sanity-checked against intent rather than only pattern-matched: ***the `authenticated` read must be a SUPERSET of the rows the write path can collide with.*** That is what makes the read-then-diff-then-insert loop safe; **the count comparison is a proxy for it**, not the thing itself. If an instantiation satisfies the counts but breaks the superset property, the instantiation is wrong.
  - 📌 **Provenance, stated rather than absorbed: the generalization from `users_id is not null` to *"that table's user-partition predicate"* is BACKEND's, not Sec's, and rides Sec's in-flight fidelity check for confirmation.** Sec's criterion was authored against `asset`'s shape and is correct there; it does not reach `eod_price`, which Sec added in the same pass. Recorded this way rather than silently corrected — **editing a ruling to make it work is how a ledger stops matching the ruling it cites.** The hazard it catches: a table with no `authenticated` SELECT policy returns **zero rows silently**, the diff reads "all new", and the ETL **mass-inserts**. ⚠ **That failure mode is created by the role split itself**, so it did not exist before this fix. A table failing that check must **fail the test** — it must **not** be worked around by widening the role. **No cross-tenant fixture required** (Sec named this explicitly so one is not added defensively).

PR-2's body must state **"no migration authored"**. ### §7.8 — Connection lifecycle

*One missing capability with four symptoms, surfaced by F/CTO questions during the ADR-042 close-gate review, 2026-08-04. Filed as **one** entry rather than four because they share a single cause: **nothing in the application ever writes `pfin.account.linked_source_id`.** Splitting them would produce four partial fixes to one gap. Verified against `main` @ `e72f652` — measurements are dated and expected to rot; the capability claim is not.*

**Connection lifecycle: disconnect, re-point, and add-accounts-to-an-existing-Item.** [V1 gap; not currently staged anywhere else]

- **Source.** F/CTO, during the ADR-042 close-gate review. Two questions, one cause. ADR-042 Decision 1 records aggregator linkage as concept 1 and states *"No new work; a link/unlink control is explicitly deferred"* — a deferral that was never converted into a staged item, so it survived only as a sentence saying "not now."

- **Measured state (dated — `main` @ `e72f652`).**
  - **`linked_source_id` is never written by any application path.** It is read throughout `api/src`; the only write-adjacent reference is `updateAttributes.server.test.ts:82`, which asserts a posted `linked_source_id` is **rejected** by `.strict()`. There is no control, no server action, and no worker path that changes it.
  - **The DB primitive already exists.** `015`'s matched-tenant fence on `pfin.account.linked_source_id` (Decision-3 canonical instance **#6**) states in its own comment: *"Covers UPDATE (**re-link path**), not just INSERT."* The fence was built for a control that was never built.
  - **Account identity is `(linked_source_id, provider_account_id)`** — the `021` partial UNIQUE index, and `042`'s ON CONFLICT arbiter.
  - **`linked_source` is unique on `(provider, external_connection_id)`** and carries **no uniqueness on `(user, institution)`**. One row per Item; nothing prevents two Items at one institution.
  - **The connect flow always mints a fresh link token.** `/accounts/connect` → `PlaidLinkConnect` → `/api/plaid/link-token`, which takes no existing-connection input. **No institution comparison exists anywhere in the connect path.**
  - **Plaid update mode is already implemented and in production** — `workers/provider-sync/src/http/linkToken.ts` passes an existing Item's `access_token` and omits `products`, per Plaid's update-mode rule. It is wired **only** to re-auth (`/api/reauth/start` → `kind: 'link_update'`).

- **The four symptoms.**
  1. **Cannot disconnect** an account from its aggregator and return it to manual.
  2. **Cannot move an account to a different aggregator** — live under [ADR-027](DECISIONS.md#adr-027)'s ratified Plaid-primary / SimpleFIN-secondary split, where an account may need to change provider.
  3. **A relink duplicates every account.** A new Item is a new `linked_source` row with a new `source_id`, and Plaid issues fresh account ids on a new Item — so **both halves of the identity change at once**, the `021` arbiter cannot match, and a second set of accounts lands beside the originals while the old Item keeps polling.
  4. **Re-selecting a connected institution mints a second billed Item.** Choosing an already-connected institution from *add connection* creates a new Item rather than reusing the existing one. **This has a recurring dollar cost** — Plaid bills per Item — and it is the symptom most likely to be hit repeatedly, because *"go add that account I skipped"* is a normal thing to do.

- **AC.**
  1. **Route symptom 4 through update mode rather than a fresh Link session.** The mechanism exists and is in production; what is missing is the entry point. Plaid update mode with account-selection is the supported flow for *"add accounts to an existing Item"* and creates no new Item and no new billing.
  2. **Detect an existing connection to the chosen institution** before minting a link token, and offer update mode instead. There is no institution comparison in the connect path today.
  3. **A re-point control** that updates `linked_source_id` on an existing account, composing with `015`'s #6 fence rather than bypassing it. **Sec joint-review-mandatory** — it writes a Decision-3 FK-shaped column across an isolation boundary.
  4. **A disconnect path** returning an account to manual (`linked_source_id = NULL`). Note the `021` index is **partial** (`WHERE linked_source_id IS NOT NULL`), so unlinked accounts leave the dedup surface by construction — confirm that is intended rather than incidental before relying on it.
  5. **Symptom 3 needs a re-identification step**, not just a re-point: on a new Item the operator must be able to say *"this existing account is that provider account on this new connection."* Both identity halves change, so no automatic match is available.

- **Dependencies.** Owner: **Architect** (control design + the #6 composition) with **Backend** (connect-flow routing) and **Sec** (joint review on AC 3). **Not blocked by ADR-042** — concept 1 is orthogonal to the closure work, and none of this waits on `059`. Independent of the `toggleAccount` removal in [ADR-042](DECISIONS.md#adr-042) Decision 1b, which governs *which accounts are imported*, not *whether a connection exists*.

- **Standing claim, measurement-independent.** The four symptoms are one capability. **Any fix that addresses fewer than all four leaves the same gap open under a different name** — that is why this is one entry, and why the *"link/unlink control is explicitly deferred"* sentence in ADR-042 should be re-pointed here rather than left as a bare deferral.
- **Dependencies.** Owner: **PM** (`BACKLOG.md`). Two-way door. No ledger move. Trivial, but deliberately booked rather than done inline — it touches six section headings that other artifacts may cite, and it is not close-gate work. **The observation worth preserving, and the reason this family is a pointer rather than an enumeration:** `supabase/CLAUDE.md` **already carries the blanket disposition** — *"read the canonical enumeration in [ADR-011](DECISIONS.md#adr-011) D3 live, **it grows**"* — **in the same sentence as a restated count.** It warns against trusting restated counts while restating one. And [ADR-037](DECISIONS.md#adr-037) D4's bracket is *itself* a correction (it superseded 14/12 with 15/13) that is now **two steps stale** — **the enumerated correction became the next stale citation.** That is the regress demonstrating itself in the artifacts, and it is the concrete case for the *prefer-a-blanket-disposition* preference recorded under **"Land the review checkpoints into the skill files."**

*Filed 2026-08-04 because it existed nowhere else. - **AC.**
  1. **Classify every match by target table.** Text matching is insufficient and has already produced wrong answers in both directions.
  2. **Fix (a) in the same PR as `059`.** Name what breaks if it follows: the nightly NAV cron fails at tenant enumeration; the dashboard shows every user the empty state with no error; accounts list, account detail and both connection surfaces lose their rows.
  3. **Two write paths must stop writing the column *before* `058` merges**, not with `059` — the account-detail toggle and the connections toggle. In the `058`→`059` window one click either aborts the migration (the biconditional assert fails after the operator step has run) or makes NAV count an account whose writes the transfer-in fence refuses.
  4. **A test that stays green while its production query starts failing must move with it** — at least one fully-mocked test asserts the old filter was called and will pass after the real query 400s.
  5. **Comments that go FALSE, not stale**, headed by one that is a *prohibition* rather than a description: a block labelled load-bearing forbids using the as-of path with a past date. The re-point **strikes that constraint**, so post-`059` it forbids the path that just became correct. **A false prohibition is undetectable by construction** — nobody tests the path they were told not to take, so its absence leaves no artifact. - **Standing claim, measurement-independent.** The surface is **non-empty and includes the net-worth path**. Its exact size is **unmeasured at filing** and is the first deliverable, not an assumption to carry forward.

### §7.10 — Cron-liveness branch harness (Sec condition on PR #340)

*Filed 2026-08-09 as Sec's stated condition on the A1 scheduled-dep-audit PR. **Filed here rather than as a PR-body follow-up number, because those are not trackers** — the standing rule after a follow-up "#N" was mistaken for a Linear ID.*

**The `scheduled-audit-liveness` job's failure branches have no committed harness — they were exercised once, at authoring.** [V1 gap; owner DevOps, Sec reviews non-vacuity]

- **Source.** Sec's merge condition on PR #340 (`scheduled-audit-liveness` in `.github/workflows/security-scan.yml`). PR #340's own body records the branches as *"exercised, three via a `gh` shim for states the live API will not produce on demand"* — **exercised at authoring, not committed.** Nothing re-runs them.

- **⚠ What is already covered, so this entry is not re-specified later as bigger than it is.** The **parser self-test is committed and runs on every invocation** — a case table over `status_of()` asserting parsed values for malformed and well-formed HTTP status lines. That half is done and needs nothing. **The gap is the FATAL branches** (404-with-repo-reachable, unregistered-workflow-with-no-history, unexpected-HTTP, state-not-active, run-history-lookup-failure, and the parser-self-test failure path itself).

- **⚠ THE HARNESS MUST ASSERT MESSAGES, NOT EXIT CODES — this is the whole point of the entry, and the job already explains why in its own body:**

  > *"This job has many branches that all exit 1. Against a fail-closed instrument a broken probe produces a false NEGATIVE that is invisible in the probe's own result: every malformed input still fails, so the probe looks like it works. The fence's best property is exactly what hides a broken harness. Asserting `"exit 1"` would therefore verify nothing here — only the parsed value discriminates."*

  A harness that asserts *"the job exited 1"* against a job whose branches all exit 1 is the **fence-that-cannot-fail** shape, arriving through the test instead of the fence. It would read GREEN in a coverage review while distinguishing nothing.

- **Why this is worth building at all, given the job is small.** This job exists because **a cron can stop existing without failing** — public-repo scheduled workflows auto-disable after 60 days of inactivity, and scheduled runs can be dropped under load. The liveness job is the observer for that. **An observer that has silently broken is worse than no observer**, because its silence is indistinguishable from health — which is the same argument that justified the job, applied one level up to the job itself.

- **Scope discipline — do NOT extend this to A1's own audit branches.** A1 (`scheduled-dep-audit.yml`) already carries its own inversion probe, which builds a throwaway tree pinned to a known-vulnerable package and asserts the same command exits non-zero. That probe is committed, runs every invocation, and was **validated in production on 2026-08-09** when A1's first scheduled run caught a real advisory. Widening this entry to cover it would duplicate working coverage.

- **AC.**
  1. **A committed harness that reaches every FATAL branch and asserts on its MESSAGE**, not on its exit status. Enumerate the branches by measurement at build time rather than from this entry — `grep -c 'echo "FATAL' ` over the job block — because a count written here goes stale silently and this file is a derived surface.
  2. **Prove the harness can fail.** For each branch, show the assertion RED when that branch's message is altered or its guard removed. **Reproduce the failure when authoring; do not port a green result** — the RT-31 leg (i) standard, which is the closest precedent in this repo.
  3. **The three branches reachable only via a `gh` shim stay shim-driven**, and the shim is committed with the harness. A branch that cannot be reached in CI is a branch with no coverage, regardless of how it was checked once.
  4. **The harness must itself be non-vacuous.** If it produces an empty branch list it must fail loudly, never pass — the same trap `(i5)`/`(T0)` guard elsewhere: an empty offender list is produced both by a healthy tree and by an instrument that has stopped matching.
  5. **Do not assert the parser self-test's cases a second time.** They are already committed; re-asserting them creates a second home for one claim.

- **Not blocking.** A1 is validated end to end as of 2026-08-09 and its own probe is committed. This hardens the observer, and the failure it guards against is silent degradation over months rather than anything live today.
