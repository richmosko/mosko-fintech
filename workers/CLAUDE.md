## What lives here

Two of the three V1 background-worker containers (the third is the V1 web-app in `api/`) per [ADR-011](../DECISIONS.md#adr-011) Decision 17 / Lock 13's hybrid 3-container runtime topology on Hetzner cax21:

- **`workers/etl/`** — `pfin_back_etl` Python ETL (BLS CPI + FMP financials ingestion → Supabase). Folded into the monorepo from the former sibling repo per [ADR-019](../DECISIONS.md#adr-019); the `github.com/richmosko/pfin_back_etl` repo is archived. Source package is `pfin_back_etl` under `src/`; deployed as a Coolify container with **Base Directory** `workers/etl/`.
- **`workers/pdf-render/`** — Node/Puppeteer PDF worker (Lock 13 mod #2). Currently a placeholder `Dockerfile`; Backend extends with the Puppeteer + Node app code at Wave 6.

Dockerfiles are **DevOps-owned** — do not edit them here; flag changes to DevOps.

## Conventions

- **ETL Python** (`workers/etl/`): `uv` + `pyproject.toml` dependency management (Python ≥3.14); **ruff** lint/format; **pytest** with marker discipline (`unit` / `integration` / `deployment` / `replay` — `--strict-markers`). Polars for dataframes; `psycopg2-binary` + SQLAlchemy for DB. Replay-parity fixtures live in `workers/etl/tests/` (`test_replay_parity.py`, `conftest.py`, `fixtures/`).
- **TenantBoundConnection (TBC)** ([Lock 13 mod #3](../DECISIONS.md#adr-011)): ANY worker code touching `pfin` constructs DB connections through the TBC wrapper — binds `users_id` at construction, asserts every query's WHERE clause carries that `users_id`. Raw `psycopg.connect()` / `psycopg2.connect()` is a **CI fence violation**. The `fence-tbc` job (production-mode + inversion-mode in one job per [ADR-019](../DECISIONS.md#adr-019) sub-decision 2) greps `workers/etl/` on every PR. **If it fires, fix at source** — never work around the fence.
- **Same-transaction audit-log**: every state-changing write to `pfin` emits its audit-log row in the **same transaction** as the state change. No retry queues, no separate transactions, no fire-and-forget. (TypeScript-side analogue lives in `api/`; the discipline is identical.)
- **Cron via Coolify**: scheduled work (the `pfin_back_etl` poll; the Wave 6 `monthly_report` cron per Gate F) runs as **native Coolify cron containers**, not an in-app scheduler. Failure/health notifications route to **Discord** (incumbent Coolify→Discord routing on cax21). Worker-scheduling decisions route to DevOps.
- **Plaid SDK** (worker side) lives in `workers/etl/`; sandbox tier in V1.0, production tier post-`SELF-212` (F/CTO-gated). New Plaid endpoints need QA sandbox-fixture coverage.

## Fail-closed / gotchas

- **The PDF worker has ZERO database access by design** ([Lock 13 mod #2](../DECISIONS.md#adr-011)). Do **not** add `psycopg` / `psycopg2` / `asyncpg` / `pg` / `node-postgres` / `supabase-py` to `workers/pdf-render/` deps — even for "logging." It reaches the data layer ONLY via the V1 web-app's `/internal/pdf-render` endpoint under a short-lived signed JWT (Lock 13 mod #1). **TBC does NOT apply to `pdf-render`** — that's a category error. The DB-isolation guarantee there is enforced by **RT-22**, an *infrastructure-credential-presence* audit on the Dockerfile (a §10 catalogued instance) — do not conflate it with the code-layer TBC fence on `workers/etl/`.
- **`service_role` is NOLOGIN — no worker "connects as service_role."** `service_role` is `rolcanlogin = f` (measured); it can never be a direct-Postgres login identity. Every worker logs in as a **NOINHERIT** role and assumes the role it needs per transaction: `set local role service_role` for privileged writes (ADR-023 write role-of-record), `set local role authenticated` + a synthetic JWT-claims GUC for RLS-scoped reads (`TenantBoundConnection.impersonate()`). Any docstring or migration comment saying a worker *connects as* `service_role` names a transport-impossible role — that phrasing is what SELF-214's Sec joint-review retracted.
  - **The two containers use DIFFERENT login roles — don't cross-copy the name:**
    - `workers/etl/` → **`pfin_etl`**, a dedicated role created by an Architect migration (SELF-214 B8 option (B), F/CTO-ratified 2026-08-02), member of `service_role` + `authenticated`. Its credential is its own, so [ADR-023](../DECISIONS.md#adr-023) condition **C1's rotation coupling does not reach the ETL** — it rotates independently of PostgREST.
    - `workers/provider-sync/` → **`authenticator`**, Supabase's shared NOINHERIT broker, per [ADR-023](../DECISIONS.md#adr-023). Its `PFIN_DB_PASSWORD` **is** PostgREST's credential — C1 applies: rotating it forces a coordinated redeploy of both.
    - The *model* is identical either way (NOINHERIT login → `SET LOCAL ROLE`), which is why worker code is unchanged between them. Only the name and the rotation blast radius differ.
  - 🔑 **`pfin_etl` ships NOLOGIN and without a password** — a credential must never sit in the repo. Switched on at deploy by an operator in **two statements, order load-bearing**: `\password pfin_etl` (prompts; hashes client-side; role still NOLOGIN → inert) **then** `ALTER ROLE pfin_etl LOGIN;`. Reversed, the role is LOGIN with no password — the state `055`'s NOLOGIN default exists to prevent. The single atomic `ALTER ROLE … WITH LOGIN PASSWORD '<plaintext>'` is **PROHIBITED** — wherever statement logging is on it writes the credential to the server log in cleartext, and Postgres does not redact passwords. Note `\password` does **not** mean "nothing is logged" — the SCRAM *verifier* is still logged; it is just not a usable credential (StoredKey/ServerKey; a client proof needs ClientKey). Its residual is an offline attack **bounded by the secret's entropy**, which is why the value must be generated — `openssl rand -hex 32` — not human-chosen. **Measurement scope:** `log_statement = ddl` was measured on the **local** stack; **V1 production does not exist yet and has not been measured** — treat statement logging as ENABLED on any target until verified there (assuming it off is failure-open), and check `log_min_duration_statement` too, which can log a statement in full independently. So **"role exists" ≠ "ETL can connect"**: fail-closed, but a required manual deploy step. `055`'s header is canonical.
  - ⚠ **NOINHERIT consequence:** the session holds **no** privileges until an explicit `SET [LOCAL] ROLE`. A `pfin` statement issued without one fails **42501**. This bites `impersonate()` in particular — its `reset role` returns you to the privilege-less login role, so the caller must assume the write role itself before writing.
  - ⚠️ **`core.py`'s global-reference path is incumbent code not yet reconciled to the V1 greenfield schema** — and this is **not** a credential problem. It targets `pfin.cpi` / `equity_profile` / `reporting_period` / `income_statement` / `balance_sheet_statement` / `cash_flow_statement` / `earning` / `asset_cat`, **none of which any V1 migration creates** (verified 2026-08-02: zero `create table` matches across `supabase/migrations/`; all eight absent from the live DB). They are cax21/pfindash.com tables carried in at the [ADR-019](../DECISIONS.md#adr-019) monorepo fold. Against V1 that path is dead under **any** credential, and it fails **loud** (`UndefinedTable`), not silently.
    - **Not a grants task** — you cannot `GRANT` on a table that does not exist, so the "Architect authors a grants migration" remedy is unexecutable. **Not an `authenticator`-flip blocker** either; the flip neither causes nor worsens it.
    - What's actually open is a **V1-scope question** — are the FMP financial-statement tables in V1 at all? — owned by **PM + Architect** and tracked independently. The ETL tables that *do* exist in V1 (`asset` 016, `eod_price` 019, `cpi_u_index` 053) are the real V1 write surface.
- **`impersonate()` is a fenced READ-ONLY primitive.** It mints a synthetic `aal2` claim, which satisfies every aal2-gated write path in the schema — including ADR-029 Decision 6's MB-1 `mfa_policy` downgrade guard. The per-tenant assertion rejects all write/DDL while the binding is active (Sec joint-review B2). Writes go **after** teardown, under an explicitly assumed write role. Do not "temporarily" widen this.
- **ETL CI is PARTIALLY wired — and the warning that used to sit here still stands, for narrower reasons.** *(Corrected 2026-08-09: this bullet said "not yet wired", which stopped being true when `.github/workflows/etl-ci.yml` landed. Measured at `832cfb7`, clause by clause, because the conclusion survives even though two of its three premises do not.)*
  - ✅ **ruff** — `ruff check src` runs on every PR touching `workers/etl/**`. **`src/` only**; full-tree ruff is deferred by the workflow's own comment.
  - ✅ **pytest** — but **`-m unit` ONLY**. That is the whole of the enforced surface.
  - ❌ **uv-aware dep-vuln audit** — still absent. `scheduled-dep-audit.yml` enumerates `git ls-files '*package.json'`, so **no Python manifest is audited at all**: `pyproject.toml` / `uv.lock` are invisible to it.
  - ❌ **`test_replay_parity.py`, the named first-green target, still does not run in CI** — its tests are marked `@pytest.mark.replay`, and `-m unit` **deselects** them. The target was never reached; the marker is why.
  - ❌ **The `integration` and `deployment` lanes are not in CI and cannot be** — they need a live database and, for anything role-sensitive, a real login credential. **⚠ This is the load-bearing part: end-to-end evidence for this worker is MANUAL, executed and recorded by hand, and is never a CI gate.** A green check on a `workers/etl/` PR means *lint on `src/` plus the unit lane* — nothing about whether the ETL can connect, construct, or write.
  - **So the original warning holds, sharpened:** do not read green CI here as lint/test enforcement of the assembled path. **`BACKLOG.md` §7.6 is the standing evidence** — S13 (production-fatal, latent ~50 migrations), S16 (a fixture converting a fatal failure into a green skip) and **S17** (every `SBaseConn` statement `42501` under the production login, invisible because every local run is a `postgres` superuser) were **all green in CI throughout**. Gaps route to DevOps.
