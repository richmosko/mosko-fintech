## §8.1 — V1 sub-version convention

V1 ships across a sequence of sub-versions rather than as a single shippable event. The convention is **V1.0 → V1.x → V1.final**: V1.0 is the first shippable mosko-fintech backend (the data-plane foothold that makes drop-replace at §8.2 possible); V1.x intermediate sub-versions deliver the remaining V1 capability surface across the §2 + ADR-004 / ADR-005 / ADR-006 scope; V1.final is the sub-version at which all three §3.4 migration-completion criteria pass. Per ADR-004 (`DECISIONS.md:353` + `:484` + `:644`), the convention was chosen because compressing V1 scope below ADR-004-locked capability and deferring delivery to V1-final-only were both rejected during ADR-004 deliberation. Specific per-version capability boundaries are Phase 4 (Scoping) / Linear-backlog territory; §8.1 commits to the *naming convention and lifecycle framework*, not to specific sub-version contents.

- **V1.0 — first shippable backend.** The minimum sub-version at which mosko-fintech can serve as a data-plane source for the §8.2 drop-replace pattern (i.e., the F/CTO can begin running residual Google Sheets views off V1.x backend data rather than off the existing manual-spreadsheet system's primary data). *Illustrative example per ADR-004 / ADR-002 Consequences (`DECISIONS.md:484` + `:644`):* V1.0 = Plaid-sourced data + manual *balances* (manual accounts with current-balance entry but without full transaction-level entry). **The specific V1.0 capability scope is Phase 4 territory**, not §8.1 — the illustrative example is provided for clarity, not as a §8 commitment.
- **V1.x — intermediate sub-versions.** Sub-versions between V1.0 and V1.final that deliver remaining V1 capability surface incrementally. Each V1.x sub-version is "shippable in framing terms" when its capability surface is delivered and parity-tested per §3.3 against the existing-system equivalent (where parity is in scope for the sub-version). *Illustrative example per ADR-004 (`DECISIONS.md:484` + `:644`):* V1.1 = full manual transaction-level entry added to V1.0's manual balances baseline. **Specific V1.x sequencing (which V1.x sub-version delivers which capability) is Phase 4 territory** — §8.1 commits to the sub-version concept, not to the per-version sequencing.
- **V1.final — all §3.4 criteria pass.** The sub-version at which all three §3.4 migration-completion criteria are satisfied: (a) parity-matrix V1-preserve completion; (b) ADR-004 / ADR-005 / ADR-006 amendment delivery; (c) existing-system retirement at N = 2 consecutive months per §3.4(c). V1.final is the conventional "V1 shipped" marker; the §3.4 criteria are the operative definition (per §8.3 cross-reference).
- **"Shippable in framing terms" at sub-version granularity.** A sub-version is shippable in §8 framing terms when its delivered capability surface is testable per §3.3 (where parity is in scope), exercises the multi-tenant infrastructure per §4.1 (RLS-enforced), and meets the §4 V1 Sec posture commitments for the capability surface it ships. Phase 4 / Linear backlog owns the specific per-version acceptance criteria (which capability surfaces a sub-version must deliver to be considered shippable, milestone-sequencing decisions, dependency ordering); §8.1 commits to the *framework*, Phase 4 owns the *contents*.

## §8.2 — Drop-replace migration pattern

The drop-replace migration pattern is the *user-continuity guarantee* during V1's data-plane transition. As V1.0 ships and subsequent V1.x sub-versions deliver remaining capability, the F/CTO's monthly-finance workflow continues uninterrupted: the V1.x backend becomes the data source for any residual existing-system Google Sheets views still in use during transition, so the data plane shifts underneath the F/CTO's working surface without requiring a hard cutover before V1.final. This is the inverse user-facing flip side of §4.6's shadow-workflow tear-down posture — §4.6 commits to the existing Google Sheet ceasing to be a *working data source* at §3.4(c) retirement; §8.2 commits to the F/CTO's monthly workflow remaining *operable* throughout the transition leading up to that retirement. Together they form the V1 transition contract: drop-replace makes §4.6 tear-down user-survivable; §4.6 tear-down is what makes drop-replace terminate cleanly.

- **V1.x backend as data source for residual Google Sheets views during transition.** Per ADR-004 (`DECISIONS.md:353`) verbatim: "V1.x backend becomes the data source for residual existing-system Google Sheets views during transition, so the Founder/CTO's monthly-finance workflow continues uninterrupted as the data plane shifts underneath." The F/CTO continues to consume residual Google Sheets views during the V1.0 → V1.final transition, but those views read from V1.x backend data rather than from the existing system's primary spreadsheets. The transition is *data-plane* (where the numbers come from), not *presentation-plane* (the F/CTO's working surface); presentation-plane migration happens incrementally as V1.x sub-versions deliver V1-native surfaces that supersede the residual Google Sheets views.
- **§4.6 shadow-workflow tear-down cross-reference.** §4.6 commits to "the existing Google Sheet stops being a working data source — V1 commits to no dual-write to the existing Google Sheet after V1 lands" + "the historical NAV import from the existing system per §2.1 Architect routing flag terminates at V1 schema population — the import is a one-time event, not an ongoing sync" + "the F/CTO retains a read-only archive of the existing spreadsheets at a Sec-acknowledged access-controlled location" + "a snapshot of the existing system's state at V1-final cutover is preserved as an audit artifact." §8.2 reciprocates from the user-continuity side: drop-replace is the *transition mechanic* by which the §4.6 tear-down posture becomes user-survivable. The drop-replace pattern terminates at §3.4(c) retirement — V1.final cutover collapses any remaining residual Google Sheets views.
- **§4.6 availability / §2.4.4 non-silent-staleness cross-reference.** During drop-replace transition, the §4.6 availability posture (best-effort uptime, no SLO, with §2.4.4 non-silent-staleness as the user-facing availability commitment) applies symmetrically across residual Google Sheets views reading from V1.x backend data and any V1-native surfaces in delivery: stale data is surfaced as stale at every consuming surface regardless of whether the consuming surface is a Google Sheet view or a V1-native UI. The user-facing availability contract does not weaken during transition; the §4.6 non-silent-staleness commitment binds equally on both sides of the drop-replace data flow.

## §8.3 — V1-done cross-reference and Phase 4 handoff

§8.3 reciprocates §3.4's V1-done definition without re-litigating its three migration-completion criteria, closes the §1.4 V1 existing-system-replacement test forward-pointer, and establishes the §8 → Phase 4 handoff boundary. V1-done is defined at §3.4 (the three criteria + N=2-months commitment on §3.4(c)); §8.3 is the milestone-framing-side anchor that V1.final corresponds to the sub-version at which all three §3.4 criteria pass. Specific sub-version sequencing — which V1.x sub-version closes which §3.4 criterion, and the per-version capability boundaries — is Phase 4 / Linear-backlog territory per ADR-004 verbatim.

- **§3.4 V1-done criteria reciprocation.** §3.4 commits to three conjunctive migration-completion criteria for V1-done: (a) parity-matrix V1-preserve completion (every "V1 preserve" line has a §2 story locked + §3.3 parity test passing); (b) ADR-004 / ADR-005 / ADR-006 amendment delivery (every locked-as-V1 amendment has its capability delivered + parity-tested); (c) existing-system retirement at N = 2 consecutive months without F/CTO reconciliation against the existing system. §8 owns the *milestone-framing scaffolding* (V1.0 → V1.x → V1.final convention + drop-replace mechanic); §3.4 owns the *criteria definition*. §8.3 is the §8-side acknowledgment of §3.4's authoritative V1-done definition; **closes the §3.4 → §8 forward-pointer at this lock** per routing flag (a) below.
- **§1.4 V1 existing-system-replacement test reciprocation.** §1.4's V1 existing-system-replacement test bullet establishes that V1 is correct when it replicates the workflows the F/CTO maintains today in the manual-spreadsheet system, plus the explicit ADR-004 amendments — per the §8 V1-done definition (anchored at §3.4). §8.3 closes this forward-pointer by anchoring the V1-done definition at §3.4 (per the reciprocation above) and confirming §1.4's existing-system-replacement framing as the V1-correctness lens that §3.4 + §8 operationalize. **Closes the §1.4 → §8 forward-pointer at this lock** per routing flag (b) below.
- **§8 → Phase 4 handoff boundary.** §8 frames the milestone scaffolding (sub-version naming convention + drop-replace migration pattern + V1-done cross-reference); Phase 4 (Scoping) / Linear backlog owns the specific milestone-sequencing decisions per ADR-004 (`DECISIONS.md:353`) verbatim. **§8 does not pre-commit any of the Phase 4 territory items below** — the milestone-framing scaffolding is intentionally separated from the milestone-sequencing decisions to keep Phase 1 (PRD) and Phase 4 (Scoping) territorially clean. Phase 4 / Linear territory includes:
  - (i) **Criterion-to-sub-version mapping** — which V1.x sub-version closes which §3.4 criterion.
  - (ii) **Per-sub-version capability boundaries** — which capability surfaces ship in which V1.x.
  - (iii) **Dependency ordering** — across §2 / §4 / §7 surfaces.
  - (iv) **Per-sub-version acceptance criteria** — at one-session-granularity per Linear issue convention.
