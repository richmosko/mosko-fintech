1. System Context

The system and the actors around it. C4 context level.

mosko-fintech is a single-tenant-in-use, multi-tenant-by-construction personal-finance application. A solo user (the Founder/CTO) connects financial institutions via Plaid; the system ingests instruments, balances, and transactions, then derives six surfaces — net worth, asset allocation, spending/income, estimated taxes, and the monthly report. The architecture is a deliberately boring monolith: one web application over one Postgres database (self-hosted Supabase), plus a small set of background workers for asynchronous and scheduled work. Multi-tenant isolation is enforced at the database layer via Supabase Auth + native RLS (ADR-011 Decision 5, Option A); the per-account account_users ACL is exercised at the RLS layer in V1 even though no sharing UI ships until V2 (Decision 7). Every isolation boundary is defended in depth — RLS + matched-tenant validation on FK-shaped columns + immutable audit-class tables + privileged-context-write discipline for all non-JWT writers (ADR-011 Decisions 1–4).

The system runs on the Founder/CTO's existing Hetzner cax21 VPS (8 ARM vCores / 16 GB / 160 GB, ~€9.50/mo) under Coolify, alongside the already-in-production pfin_back_etl Python ETL. Phase 3 extends that footprint rather than greenfielding it: per ADR-011 Decision 17, V1 spreads work across three Coolify containers — pfin_back_etl (Python; gains the monthly-report cron, the Plaid scheduled-poll, and the NAV worker on top of incumbent BLS + FMP ingestion); the V1 web app (SvelteKit + TypeScript; owns the Plaid webhook handler and all user-facing read/render paths via a SECURITY INVOKER read-composition helper); and a new Node PDF-render worker (Puppeteer, rendering through the V1 app's authenticated render URL — never touching the database directly). External dependencies are Plaid (aggregation + webhooks) and the two reference-data feeds already wired into pfin_back_etl (BLS CPI-U; FMP prices).

Framework locked. The V1 web app is built on SvelteKit (Svelte 5) per ADR-015 — closing the Phase 2 ↔ Phase 3 coupling point per ADR-012 and anchoring the V1-web-app container in the ADR-011 Decision 17 hybrid 3-container topology. See §4 for the row decomposition (V1 web-app / ingestion+cron / PDF render worker) and §4.1 for the server-source allowlist anchoring the RT-26 CI grep fence. No Tailwind; styling consumes ADR-014's two-tier tokens natively via Svelte component-scoped <style>.
Scope fence honored. pfin_back_etl's FMP / stock-screening ingestion-architecture detail is intentionally left unresolved here. The candidate-P3 disposition (ADR-011 Decision 20, PM-ratified 2026-05-29: ingest, no V1 UI) holds; the ingestion-architecture detail lands in the Worker / Data-model sections. This overview names FMP only at the container / topology level.

3. Data Flow

One sequence diagram per primary user story. Only diagram flows with non-trivial design choices.

At the system level there are two write contexts and one read/render path. User-session writes (settings, manual entry, as-of-date queries) carry a Supabase Auth JWT and are gated by RLS WITH CHECK at the database. Privileged-context writes (Plaid sync, NAV computation, the monthly-report cron, and reference-data ingestion) run under service_role with no JWT, so tenant correctness is bound in code via TenantBoundConnection and recorded in an explicit audit log (ADR-011 Decision 1, the privileged-context-write discipline). Both contexts land in immutable audit-class tables for money-correctness surfaces. All reads flow through a single SECURITY INVOKER read-composition helper (user-session only — never invoked from a worker), which is also the render source the PDF worker reaches through the V1 app rather than the database.

This is the system-level overview only. A per-story sequenceDiagram is drafted with each surface's own later section (Data model, Plaid integration, Workers, etc.) — those carry the non-trivial flow-specific design choices.

4.1 V1 server-source surface — RT-26 allowlist anchor

The V1 web-app container's server-side source surface is enumerated below as the allowlist of permitted surfaces for the RT-26 grep fence. The fence searches the V1 web-app source tree (src/** plus the repo-root config files — see below) for any reference to SUPABASE_SERVICE_ROLE_KEY; references in files matching an allowlist glob are permitted, all others trip the grep at PR-time (fail-closed). The structural consequence: universal loaders (+page.ts / +layout.ts) and any other non-allowlisted surface are by-construction-banned from referencing service_role — closing the client-bundle-leak failure mode by the same fence that closes the RLS-bypass failure mode.

RT-26 is a V1-SHIP-BLOCK + HIGH severity posture obligation per SECURITY §4.2; V1 cannot ship with the fence absent or unenforced over this surface (parallel to RT-05's hard-line shape; critical-severity reserved for credential-class admission boundaries per the §4.5 rubric). The fence is allowlist-shaped (not wrapping-shaped) — it enumerates permitted surfaces by file path rather than wrapping the env-var reference in a sanctioned helper. Wrapping-shaped fences silently fail-open when a new server route lands under time pressure and reaches for the raw env var; allowlist-shaped fences fail-closed because any new reference outside the allowlist trips the grep at PR-time. Adding new allowlist entries requires Sec-consult + ADR amendment at the surface-introducing lock.

Repo-root build-config exclusion. Repo-root build-config files (vite.config.{ts,js}, svelte.config.js) are NOT on the allowlist; any reference to SUPABASE_SERVICE_ROLE_KEY in these surfaces trips the fence (build-time injection into the client bundle is the failure mode the exclusion catches). These files are inside the V1 web-app source tree but outside src/**; the fence covers them under its src/** + repo-root scan even though they don't match an allowlist glob.

Worker-entry codepaths covered under separate fence layers (named here for completeness; not in the V1 web-app RT-26 grep scope):

  • pfin_back_etl (Python container) — uses the TenantBoundConnection class code-layer fence per ADR-011 Decision 17 / Lock 13; CI grep enforces the class as the only allowed Postgres-client entry point (no raw psycopg2.connect() outside the class). Code-layer §10 fence per ADR-011 Decision 4 Privileged-context surfaces bullet (parallel to RT-26's V1-web-app code-layer fence; not in Decision 4's catalogued-instance numbered list — that list catalogues RT-22 first, RT-26 second).
  • Node PDF worker container — covered by the RT-22 infrastructure-credential-presence fence: no SUPABASE_* env vars; no Postgres client in Dockerfile; only PDF_WORKER_SIGNING_KEY per SD-20. RT-22 verifies absence at PR-review on every Dockerfile change. PDF worker reaches the data layer only via the V1 web-app's /internal/pdf-render endpoint under a short-lived signed JWT (Lock 13 mod #1 contract — preserves Lock 12 mod #1 read-path-only fence by-construction).

Three-layer §10 defense composition (per ADR-011 Decision 4 + SECURITY §4.2):

  1. Code-layer — this RT-26 allowlist CI grep fence on the V1 web-app server-source surface enumerated above.
  2. JWT-shape-layer — RLS predicate users_id = auth.uid() bound under authenticated tier (existing).
  3. Infrastructure-credential-presence-layer — Phase 3 ops bounds SUPABASE_SERVICE_ROLE_KEY runtime presence to allowlisted surfaces.

All three layers required; failure of any one is recoverable iff the other two hold. RT-26 enforcement details — fence implementation, allowlist registry location, PR-time grep trigger — land at Phase 5 (CI pipeline build).
