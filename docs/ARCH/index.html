1. System Context

The system and the actors around it. C4 context level.

mosko-fintech is a single-tenant-in-use, multi-tenant-by-construction personal-finance application. A solo user (the Founder/CTO) connects financial institutions via Plaid; the system ingests instruments, balances, and transactions, then derives six surfaces — net worth, asset allocation, spending/income, estimated taxes, and the monthly report. The architecture is a deliberately boring monolith: one web application over one Postgres database (self-hosted Supabase), plus a small set of background workers for asynchronous and scheduled work. Multi-tenant isolation is enforced at the database layer via Supabase Auth + native RLS (ADR-011 Decision 5, Option A); the per-account account_users ACL is exercised at the RLS layer in V1 even though no sharing UI ships until V2 (Decision 7). Every isolation boundary is defended in depth — RLS + matched-tenant validation on FK-shaped columns + immutable audit-class tables + privileged-context-write discipline for all non-JWT writers (ADR-011 Decisions 1–4).

The system runs on the Founder/CTO's existing Hetzner cax21 VPS (8 ARM vCores / 16 GB / 160 GB, ~€9.50/mo) under Coolify, alongside the already-in-production pfin_back_etl Python ETL. Phase 3 extends that footprint rather than greenfielding it: per ADR-011 Decision 17, V1 spreads work across three Coolify containers — pfin_back_etl (Python; gains the monthly-report cron, the Plaid scheduled-poll, and the NAV worker on top of incumbent BLS + FMP ingestion); the V1 web app (SvelteKit + TypeScript; owns the Plaid webhook handler and all user-facing read/render paths via a SECURITY INVOKER read-composition helper); and a new Node PDF-render worker (Puppeteer, rendering through the V1 app's authenticated render URL — never touching the database directly). External dependencies are Plaid (aggregation + webhooks) and the two reference-data feeds already wired into pfin_back_etl (BLS CPI-U; FMP prices).

Framework locked. The V1 web app is built on SvelteKit (Svelte 5) per ADR-015 — closing the Phase 2 ↔ Phase 3 coupling point per ADR-012 and anchoring the V1-web-app container in the ADR-011 Decision 17 hybrid 3-container topology. See §4 for the row decomposition (V1 web-app / ingestion+cron / PDF render worker) and §4.1 for the server-source allowlist anchoring the RT-26 CI grep fence. No Tailwind; styling consumes ADR-014's two-tier tokens natively via Svelte component-scoped <style>.
Scope fence honored. pfin_back_etl's FMP / stock-screening ingestion-architecture detail is intentionally left unresolved here. The candidate-P3 disposition (ADR-011 Decision 20, PM-ratified 2026-05-29: ingest, no V1 UI) holds; the ingestion-architecture detail lands in the Worker / Data-model sections. 3. Data Flow

One sequence diagram per primary user story. Only diagram flows with non-trivial design choices.

At the system level there are two write contexts and one read/render path, all composing under the ADR-011 Decision 4 §10 three-layer defense (code-layer / JWT-shape-layer / infrastructure-credential-presence-layer; layer definitions in SECURITY §4.2; V1 catalogued instances in the ADR-011 Decision 4 ledger).

User-session writes (settings, manual entry, as-of-date queries per ADR-005 / Lock 14 / Lock 15) flow browser → SvelteKit +server.ts route handlers (with the session JWT forwarded via src/hooks.server.ts per ADR-015) → Supabase Postgres. The session JWT is issued by Supabase Auth on the authenticated tier (ADR-011 Decision 5); it carries an auth.uid() claim that the JWT-shape-layer (RLS predicate users_id = auth.uid() enforced at the DB) consumes to gate every write with RLS WITH CHECK. The Auth row in §4 supplies the JWT shape; the JWT-shape-layer itself lives at the DB.

Privileged-context writes (Plaid sync, NAV computation, the monthly-report cron, and reference-data ingestion) run with no user-session JWT — they use service_role-tier credentials. Under service_role, RLS is bypassed by design; CHECK / UNIQUE / FK constraints + BEFORE/AFTER triggers all still fire — tenant correctness is bound in code and asserted at the DB through orthogonal mechanisms (matched-tenant triggers per ADR-011 Decision 3 cross-tenant FK-bypass family; SD-00 immutability per Decision 14 / Lock 10). Two distinct privileged-context surfaces exist:

  • pfin_back_etl (Python container) — Plaid scheduled-poll + NAV + BLS + FMP + monthly-report cron. Tenant correctness is bound in code via the TenantBoundConnection class (CI grep enforces the class as the only allowed Postgres-client entry point) + same-transaction audit-log emission per the ADR-011 Decision 1 privileged-context-write discipline. Parallel code-layer fence to the V1 web-app's RT-26 allowlist (not in the Decision 4 catalogued-instance numbered list, which names RT-22 first and RT-26 second).
  • V1 web-app Plaid webhook handler (SvelteKit src/routes/api/plaid/webhook/+server.ts) — allowlisted §4.1 surface inside RT-26's code-layer audit scope. Handles the RT-02 Plaid Items table + RT-05 webhook signature verification critical-severity surfaces. Webhook handler obtains a service_role Supabase client via src/lib/server/** factory (the natural home for the allowlisted surface per §4.1); writes are bound in same-SERIALIZABLE-transaction with audit-log emission per the same Decision 1 discipline (analogous to the pfin_back_etl shape; TypeScript-side helper rather than the Python TenantBoundConnection class). Detailed flow in §3.1.

Both write contexts land in immutable audit-class tables for money-correctness surfaces (account_trans, reconciliation_event, monthly_report, plaid_item_state_history; SD-00 immutability per ADR-008) and emit an explicit audit-log row (pfin.plaid_sync_audit per ADR-011 Decision 17 mod #8 cross-language schema-as-contract).

All reads flow through a single SECURITY INVOKER read-composition helper (user-session only — never invoked from a worker), which is also the render source the PDF worker reaches through the V1 web-app's /internal/pdf-render endpoint rather than the database directly. The PDF worker container has no Supabase credentials by Dockerfile audit (RT-22 — the first catalogued §10 instance per ADR-011 Decision 4 ledger; infrastructure-credential-presence layer enforced in the PDF worker container). Detailed flow in §3.2.

3.2 PDF render cross-container handoff

4.1 V1 server-source surface — RT-26 allowlist anchor

The V1 web-app container's server-side source surface is enumerated below as the allowlist of permitted surfaces for the RT-26 grep fence. The fence searches the V1 web-app source tree (src/** plus the repo-root config files — see below) for any reference to SUPABASE_SERVICE_ROLE_KEY; references in files matching an allowlist glob are permitted, all others trip the grep at PR-time (fail-closed). The structural consequence: universal loaders (+page.ts / +layout.ts) and any other non-allowlisted surface are by-construction-banned from referencing service_role — closing the client-bundle-leak failure mode by the same fence that closes the RLS-bypass failure mode.

RT-26 is a V1-SHIP-BLOCK + HIGH severity posture obligation per SECURITY §4.2; V1 cannot ship with the fence absent or unenforced over this surface (parallel to RT-05's hard-line shape; critical-severity reserved for credential-class admission boundaries per the §4.5 rubric). The fence is allowlist-shaped (not wrapping-shaped) — it enumerates permitted surfaces by file path rather than wrapping the env-var reference in a sanctioned helper. Wrapping-shaped fences silently fail-open when a new server route lands under time pressure and reaches for the raw env var; allowlist-shaped fences fail-closed because any new reference outside the allowlist trips the grep at PR-time. Adding new allowlist entries requires Sec-consult + ADR amendment at the surface-introducing lock.

7.1 Plaid integration endpoint posture

Plaid is the dominant V1 integration; the surface spans seven outbound endpoints + one inbound endpoint across two consuming containers (V1 web-app SvelteKit + pfin_back_etl Python) with materially different per-endpoint posture (rate-limit per Plaid product; retry semantics differ across scheduled-poll vs webhook vs on-demand vs Link; idempotency only on write paths). §7.1 carries the per-endpoint behavioral contract; the §3.1 webhook flow and the §4.1 RT-26 allowlist are referenced, not re-narrated.

Endpoint enumeration. V1 consumes the following Plaid endpoints. Direction is named per endpoint; the consuming container is named per the ADR-011 Decision 17 / Lock 13 hybrid three-container topology.

Outbound (V1 web-app SvelteKit):

  1. Plaid Link link_token create — server-side via +server.ts route handler. Generates a short-TTL link_token returned to the browser for the Plaid Link flow (PRD §2.4.1 account onboarding). No credential data flows to or from V1 servers during the user's institution-credential entry.
  2. Plaid /item/public_token/exchange — server-side via +server.ts route handler. Exchanges the browser-returned public_token for a long-lived access token. The access token is encrypted via Supabase Vault / pgsodium and stored as encrypted BYTEA in pfin.plaid_items.access_token_encrypted per SD-03 credential-class storage (application-layer encryption, KMS-backed, audit log on rotation; per ADR-011 Decision 8 / Lock 4). Allowlisted §4.1 surface — canonical second RT-26 allowlist entry per ADR-016 + the SECURITY §4.2 Webhook-allowlist annotation convention. Credential-class admission surface; service_role posture inherits from the SD-03 storage-class write-path stricture (same posture rationale as endpoint 9 webhook write path: credentials are categorically stricter than even high-tier financial-data classes per SECURITY §4.2).
  3. Plaid /item/remove — server-side via +server.ts route handler. Allowlisted §4.1 surface — canonical third RT-26 allowlist entry per ADR-016 + the SECURITY §4.2 Webhook-allowlist annotation convention. Anchors the SD-03 bounded-Item-active-only retention commitment per SECURITY §4.2 + §4.6 — on Item-deletion, V1 calls /item/remove server-side to revoke the access token at Plaid before deletion-class operations against the local credential row. service_role posture required to read vault.decrypted_plaid_access_token per Lock 4 mod #1 before invoking Plaid /item/remove (the decrypted access token must be presented to Plaid in the revoke call).

Outbound (pfin_back_etl Python; scheduled-poll cadence):

  1. Plaid /transactions/sync — pfin_back_etl scheduled-poll for Plaid Transactions product, per ADR-011 Decision 17 / Lock 13 mod #3; iterates per-tenant Plaid Items reading the decrypted access token via the vault.decrypted_plaid_access_token view per Lock 4 mod #4. Cursor-resume semantics on retry (Plaid's cursor parameter preserves delivery-once across transient failures).
  2. Plaid /investments/holdings/get — pfin_back_etl scheduled-poll for Plaid Investments product holdings (PRD §2.4 Investments coverage).
  3. Plaid /investments/transactions/get — pfin_back_etl scheduled-poll for Plaid Investments product transactions.
  4. Plaid /accounts/get — pfin_back_etl instrument enumeration; newly-available-account detection per PRD §2.4.1 on resync (compares Plaid's current account list against stored SD-01 account-share-decision set).

Inbound (V1 web-app SvelteKit; reactive surface):

Auth shape. V1 consumes Plaid under a two-tier auth posture:

  • Per-V1-system credentials (PLAID_CLIENT_ID + PLAID_SECRET; sandbox vs production environment selection per ADR-002 §6.0) authenticate V1 as a Plaid application across all V1↔Plaid API surfaces (endpoints 1–8 above). Stored as per-container env-vars on both V1 web-app and pfin_back_etl containers per §5 Credentials surface; never client-facing.
  • Per-Item access tokens (Plaid-returned long-lived tokens, one per linked institution-Item) authenticate V1 to specific tenant-institution data on per-product endpoints (endpoints 4–8). Tokens are stored as encrypted BYTEA in the storage column pfin.plaid_items.access_token_encrypted per SD-03 (credential-class; application-layer encryption via Supabase Vault / pgsodium; KMS-backed; retention = bounded-Item-active-only per SECURITY §4.6 data-retention bullet); decrypted-value access via the vault.decrypted_plaid_access_token view is service_role-only per Lock 4 mod #1 — the pgsodium decrypt-view permission gap was Sec's load-bearing catch at Lock 4.

The Plaid webhook signing secret (PLAID_WEBHOOK_SECRET) is a third secret with distinct posture: it authenticates Plaid → V1 on the inbound webhook surface (endpoint 9), verified at the handler per RT-05; stored as a V1-web-app-container env-var only per §5 Credentials surface. SECURITY §4.2 carries the credential-class posture obligations; §7.1 names the secret only at the auth-shape axis.

Rate-limit + throughput posture. Plaid two-product throughput across a single tenant (consolidates App B §7.2 (a) Architect Phase 3 forward-pointer at this canonical home). V1 ships Plaid Transactions + Plaid Investments as concurrently-metered products on the same Item per PRD §7.2 scale baseline; rate-limit posture composes accordingly:

  • Scheduled-poll cadence — pfin_back_etl polls /transactions/sync + /investments/holdings/get + /investments/transactions/get on a daily-snapshot cadence (aligned with the V1 daily-snapshot product identity per PRD §6 product-identity boundary). Per-Item per-product polling is serialized within pfin_back_etl; concurrent multi-Item polling is bounded by pfin_back_etl's worker concurrency posture (Phase 5 sizing — see ADR-011 Decision 17 worker-concurrency open question). Webhook arrival is the primary signal for fresh sync; the scheduled-poll is the catch-up / fallback path per Lock 13 hybrid posture.
  • On-demand surface from V1 web-app — /transactions/sync is also reachable from V1 web-app +page.server.ts paths under on-demand triggers (e.g., post-re-auth resync per PRD §2.4.4). On-demand calls are user-session-bounded (one outstanding per Item per user-session); the global rate budget is shared with pfin_back_etl's scheduled-poll.
  • Plaid product-tier quota — V1 operates under Plaid's per-product per-month quota at the PRD §7.1 ≤$50/month cost ceiling; concrete quota sizing is Phase 5 reconciliation against actual Plaid bill per PRD §7.1 (a) Architect-Phase-3 cost-shape forward-pointer (§7.1 Plaid endpoint-axis names the posture; §8 Trade-offs carries the cost-architecture rationale when §8 drafts).
  • Throughput shape at V1 single-user scale — Plaid's per-Item rate ceiling materially exceeds V1's per-Item polling cadence; the near-term rate-limit risk surface is webhook burst (Plaid can fan out webhook events on Item state-change at higher cadence than scheduled-poll). Lock 4 mod #3 plaid_webhook_id UNIQUE idempotency gate handles duplicate-event coalescing by-construction; sustained burst would surface at pfin.plaid_sync_audit row growth as a Phase 5 observability concern.

Retry + idempotency posture.

  • Webhook idempotency (inbound, endpoint 9) — plaid_webhook_id UNIQUE constraint per Lock 4 mod #3; ON CONFLICT → ROLLBACK + 200 OK so Plaid's timeout-retry behavior coalesces duplicate webhooks at the DB layer by-construction. The full sequence (signature-verify → idempotency-gate → tenant-resolution → audit, under the transaction-isolation posture committed at §3.1) lives at §3.1; §7.1 carries only the endpoint-axis contract.
  • /transactions/sync cursor-resume (outbound, endpoint 4) — Plaid's cursor parameter is V1's primary delivery-once mechanism on the scheduled-poll path. On transport / Plaid-5xx / rate-429 failure, pfin_back_etl retries with the last-acknowledged cursor (advanced only on successful DB commit of the returned page); duplicate-row defense is shared with the webhook path via the existing dedup machinery (per-account import_hash + plaid_transaction_id partial UNIQUE per Decision 8 / Lock 4).
  • /item/public_token/exchange (outbound, endpoint 2) — single-shot; no retry on success (token-exchange-once contract). On Plaid-5xx, V1 surfaces the failure to the user-facing onboarding flow per PRD §2.4.1; the public_token itself has a short TTL on Plaid's side and is not reused after expiry.
  • /item/remove (outbound, endpoint 3) — single-shot with retry on transport / 5xx; must complete before V1 declares the Item revoked to honor the SD-03 bounded-Item-active-only retention commitment. Failure semantics: on persistent failure, V1 logs the failure + retains the encrypted access token (continued credential-class storage) + surfaces a Phase 5 detail-design retry-or-manual-intervention queue (analogous to PRD §2.4.4 non-silent-staleness pattern — never silently delete-local-without-revoking-Plaid-side).
  • Read-only outbound endpoints (5, 6, 7, 8) — idempotent at Plaid's contract; retry on transport / 5xx is safe (V1's downstream DB writes are idempotent under the dedup + INSERT-new-version disciplines per Decisions 13–15). No application-layer idempotency surface beyond what Plaid's read contract provides.
  • Plaid Link link_token create (outbound, endpoint 1) — single-shot per onboarding flow; failures surface to the user-facing onboarding flow per PRD §2.4.1; short-TTL token is not reused after expiry.
