**A-1 [c] §2.3.1 — "seeded with the user's existing categorization at V1 bootstrap."**

**A-2 [c] §2.3.1 — "each transaction … carries its own bucket assignment" — FINAL WORDING (S-1 ruled (b), F/CTO 2026-08-22, sitting-log.md).**
The GL-era carrier already exists and is not a transaction column: `account_trans` is whole-row immutable (ADR-011 D14 / Lock 10); the assignment lives in the **mutable 1:1 annotation overlay** (`023`, re-targeted at `084`), with reclassification history at `031`.
Proposed replacement for the assignment sentence (current text: "…through which each transaction is independently classified to a Sub-Cat (and its parent Cat by inheritance) at the per-transaction level — unlike the per-symbol assignment pattern in §2.2.1, transactions are per-event rather than per-instrument, so each transaction carries its own bucket assignment."):
> "…through which each classifiable **item** — an unsplit transaction, or a split child created on the §2.4.3 split path; the classify queue's single unit of work — is independently classified to a Sub-Cat (and its parent Cat by inheritance). Unlike the per-symbol assignment pattern in §2.2.1, cash-flow classification is per-event rather than per-instrument, so each classifiable item carries its own bucket assignment. **Classifiability boundary (F/CTO ruling 2026-08-22):** the classify queue comprises items outside the mechanical posting vocabulary — a transaction whose GL posting is mechanically determined (the ADR-058 posting-vocabulary split: trades, stock splits, transfers-in-kind and their instrument legs) is not user-classified; the §2.3 cash-flow surfaces (§2.3.2 / §2.3.3 / §2.3.4) sum only cash-flow-annotated items. The concrete membership predicate is Architect-defined at the posting-vocabulary layer and is not enumerated here. A transaction spanning multiple buckets takes two steps in two places: split it on the §2.4.3 split path, then classify each child independently here — the classify UI is whole-item and offers no one-step split-and-classify. Classifying a transfer does not by itself cancel it out of the cash-flow picture (a journal-less transfer resolves to Suspense, not a clean offset), and the assignment UI's copy makes no such promise. Assignment is carried in the mutable per-item annotation layer over the immutable transaction ledger, and re-assignment is history-preserving (Lock 10; ADR-031). **Cross-domain corrections (F/CTO rulings 2026-08-22, S-4 (a) + E1 (a)):** the assignment UI classifies within the cash-flow domain only; a transaction recorded in the wrong domain (cash-flow ↔ AcctSetup) is corrected through the §2.4.3 edit / reverse-and-replace flow — a domain move is a re-posting, and reverse-and-replace is the ledger's sanctioned re-post. A correction produces exactly **one** new item to classify — the replacement; the reversal row is bookkeeping the user never meets in the queue and never classifies, netting structurally against its original."
(One-edit passage per sitting item 7's convergence rule: the item-grain definition, the S-5 two-step sentence, and the S-4/6a no-cancel-out clause are integrated in a single pass, not appended sequentially — "stock splits" in the mechanical example list is deliberate, so the sentence cannot be read against classifiable split children. §2.4.3's two mechanisms — the split path (S-5's) and edit/reverse-and-replace (S-4's) — are cited separately, never interchangeably, per the corrected item 7. The example list stays strikeable by Architect. **E1 gate RELEASED (sitting items 8 + 8a):** reversals are excluded from the queue, never classified, and net structurally via `replaces_trans_id`; the pointer sentence is final as worded above. Deliberately absent from the passage: any promise that §2.3 totals equal GL totals — they legitimately differ net-of-reversals (the both-correct-not-equal Suspense offset, BOOKED at BACKLOG §7 per 8a, not a PRD fact).)
