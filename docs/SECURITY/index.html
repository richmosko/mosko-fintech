4. Security and compliance posture

§4 lands V1's security and compliance posture — the canonical reference layer for tenant isolation, credential handling, derivative-persistence + staleness, the sensitive-data classification matrix, the Phase 3 RLS test catalog, and the cross-cutting posture commitments (data retention, availability/uptime, incident handling). §4 is Security Reviewer primary-authored (first Sec primary-authorship in Phase 1 Step 3; prior Sec engagements were six at-lock pass-with-comments verdicts on PM-authored §2 sections). The canonical-reference layer is captured at ADR-008 with bullet-level posture commitments at §4.1–§4.6; ADR-008 establishes the immutability boundary for the six canonical Sec axes, the 14-entry sensitive-data classification matrix, the 15-entry RLS test catalog, the V1 retention/availability/incident-handling baseline, and the two pattern divergences from PM-led drafting (hybrid format + two-stage drafting). §4 closes ADR-002 §7.0 missing-content gaps #4 + #6 + partial-#5; consumed by Phase 3 architecture work, Phase 5 migration design, Phase 6 PR review (Security Reviewer mandatory on every PR touching auth / data handling / external APIs / secrets / financial calculations), and Phase 7 incident handling.

§4.1 Tenant isolation posture

V1 isolation primitives — axes (i)–(iv) per ADR-008 Decision 1.

§4.1 anchors mosko-fintech V1's isolation primitive: tenant_id is the V1 isolation boundary; every other axis-of-parameterization on user-data query paths (scope, tax_treatment, date, account_id, target_month) is a data attribute or inclusion filter operating within the tenant boundary, not a parallel isolation boundary alongside it. This sub-section consolidates the four canonical Sec axes (i)–(iv) elevated through the six §2.x at-lock passes into V1-locked posture commitments per ADR-008 Decision 1. The §4.4 matrix's tenant-scoped, tenant-scoped-with-app-encryption, and tenant-scoped-derivative storage-protection-class values all assume the §4.1 isolation primitive as foundation (see §4.4); the §4.5 RLS test catalog's 14 active tests verify the posture commitments below either directly or as adjacent extensions (see §4.5).

  • tenant_id is the V1 isolation boundary (axis i — canonical clause). Every user-data table carries a tenant_id column; every read against a user-data table is enforced via Row-Level Security at the database policy layer to return only rows whose tenant_id matches the requesting tenant context. RLS enforcement is non-optional and is exercised (not bypassed) on the V1 single-user-tenant test path per ADR-002 §1.4 — single-user V1 is the deployment posture, not the isolation posture; the isolation posture is multi-tenant from day one. The 14 V1-mandatory tests in §4.5 verify this primitive across read paths, write paths, worker-context paths, and the test-environment posture; concrete RLS policy implementation is Architect Phase 3 per routing flag (a).
  • Multi-scope ownership is a tenant-scoped data attribute, NOT an isolation boundary (axis ii — canonical clause). The ownership-scope label set during account onboarding (e.g., personal, trust, retirement custodial, HSA) per ADR-004 Decision B is a scope column on user-data rows. Scope filtering happens at the application query layer above the RLS boundary — a tenant's query for "personal-scope NAV" runs as WHERE tenant_id = $1 AND scope = 'personal' where the tenant_id clause is RLS-enforced and the scope clause is application-layer-applied. V1 user-facing surfaces render full-household-only (per §2.1.7 / §5.1 per-scope deferral); the data model carries scope from V1 bootstrap so V2 per-scope rendering ships without a data migration. Scopes are user-owned data labels; tenant isolation is the isolation boundary.
  • tax_treatment is an inclusion-filter attribute, NOT an isolation boundary (axis iii — canonical clause). The three-way tax_treatment enum per ADR-002 §1.6 (taxable / tax-deferred / tax-free) on each account is a data attribute that filters which holdings contribute to specific aggregations (e.g., §2.5.4 Unrealized Tax Liability aggregates only tax_treatment IN ('taxable') per (π) lock). Like scope, tax_treatment filtering happens at the application query layer above the RLS boundary; tenant_id remains the isolation boundary across all tax_treatment filter combinations. The tri-axis query parameterization (tenant_id × scope × tax_treatment × date) verified at RT-06 is the canonical V1 query-shape envelope; future V2+ attributes that surface as additional inclusion filters operate within the same envelope and do NOT relax the isolation boundary.
  • Write-path RLS symmetry: write paths inherit the tenant-scoping the read paths enforce (axis iv — canonical clause). No write path in V1 bypasses the tenant-scoping the read path enforces. The four §2.4.x mutation paths (account onboarding, manual account creation, manual transaction entry / edit / split / skip / reconcile, re-auth completion) per §2.4.5 are tenant-scoped at the database policy layer; same applies to the §2.6.2 commentary write path (RT-11) and the §2.6.4 owner-identification settings-store write path (RT-12). Manual-entry write paths carry elevated integrity risk relative to Plaid-ingested data — a user can author a buy five years ago at any price, with direct impact on cost basis and downstream realized-G/L computation per §2.4.5 elevated-integrity posture. V1 acknowledges the asymmetry as a write-path-integrity concern distinct from but downstream-of the write-path-RLS commitment; the specific integrity mechanism is Architect Phase 3 territory routed through the §2.4 manual-entry write-path Architect/Sec joint flag.
  • Single-user V1 + multi-tenant infrastructure from day one (§7.3 cross-reference; closes §7.2 isolation-at-scale forward-pointer). Per ADR-002 §1.4 + §7.3 verbatim. The V1 usage model is explicitly single-user; the V1 isolation posture is multi-tenant. Isolation-at-scale posture per §7.2 forward-pointer (e) lands here: at V1 scale (single tenant) the §4.1 isolation primitive is exercised on every query under RLS; the scale-dimension question of how the isolation primitive holds at V2 multi-user scale (RLS query performance, cross-tenant query-plan stability, concurrent-tenant cron job isolation per RT-09) is Architect Phase 3 territory per §7.2 routing flag (b). §4.1 commits to the posture — RLS scale is first-class from day one even at single-user-V1 test paths; the implementation shapes are downstream. Closes §7 routing flag (e)'s isolation-at-scale forward-pointer at §4 lock.

§4.2 Credential and external-API posture

V1 credential-class data class (SD-03 Plaid access tokens) + external-API surface (Plaid OAuth + webhooks). The two critical-severity tests (RT-02, RT-05) mark this boundary.

§4.2 lands V1's posture for credential-class data and the external-API surface that introduces it. mosko-fintech V1 has exactly one credential-class data class — SD-03 Plaid access tokens — and exactly one external-API surface that handles credentials — the Plaid OAuth flow + webhook channel per §2.4.1 + §2.4.4. The asymmetry between credential-class data and the broader sensitive-data surface is intentional: credentials get categorically stricter handling than even high-tier financial-data classes because compromise yields direct unauthenticated access to a downstream system (the user's institution data via Plaid), not just exposure of stored financial state. The §4.5 catalog's two critical-severity tests (RT-02, RT-05) are V1-ship-blockers per ADR-008 Decision 3; the critical-severity tier exists at V1 specifically to mark the credential-class boundary.

  • Plaid OAuth flow integrity — credentials stay at the institution; mosko-fintech holds only a Plaid-mediated access token. Per §2.4.1 verbatim. The Plaid Link flow exchanges a short-TTL Link token → public token at the client → server-side /item/public_token/exchange for a long-lived access token; the institution credentials the user enters at the institution never touch mosko-fintech servers, and the access token never touches the client. Redirect URI is allowlist-bound. §4.2 reaffirms as V1 posture.
  • SD-03 Plaid access tokens carry credential-class storage protection (RT-02). Per §4.4 SD-03 row: application-layer encryption, KMS-backed, audit log on rotation, tenant-scoped non-negotiable, never client-facing. Retention is bounded-Item-active-only — server-side deletion on Item-deletion, not merely flagged-inactive. RT-02 verifies tenant isolation on the Plaid Item table where SD-03 + SD-02 co-locate; RT-02 is critical-severity per ADR-008 Decision 3 — Plaid Item table cross-tenant compromise is the V1-ship-block scenario. Concrete storage shape (per-tenant key derivation, KMS-backed mechanism, audit-on-rotation surface) is Architect Phase 3 per routing flag (b).
  • Webhook signature verification gates production credential-state mutation (RT-05; hard Sec hard-line for V1 ship). Per routing flag (c). Every incoming Plaid webhook payload's signature is validated against the configured Plaid webhook signing secret before the payload routes to any credential-state mutation path; invalid-signature payloads are dropped with audit-log entry. RT-05 verifies under the adversarial-input battery (signature stripping, signature substitution from another Plaid app's secret, replay of valid-but-stale signatures, payload-body tampering with signature retained). Sec hard-line: V1 cannot ship with RT-05 failing or unimplemented. Routing flag (c) carries the Sec-sign-off-before-V1-ship requirement.
  • Four credential-error states handled non-silently (per §2.4.4 verbatim). The data model distinguishes at minimum (a) ITEM_LOGIN_REQUIRED (institution credentials invalid — user re-auths via Plaid Link); (b) INSTITUTION_DOWN (Plaid reaches the institution but it's offline — no user action required); (c) institution-side grant revoked (the institution withdrew Plaid's grant; user acts at the institution side); (d) user-side grant revoked at the institution (user revoked Plaid on the institution's portal; user re-authorizes there before re-auth here can complete). Finer UX presentation of (b) / (c) / (d) is Phase 2 territory; the data-model distinction holds in V1. Re-auth UX is in-session only — mosko-fintech sends no re-auth-link emails or SMS; institution credentials are entered only inside the authenticated app session, through Plaid Link itself. Pre-emptive Plaid re-auth reminders are V2+ per BACKLOG.md §5.4 with Sec-consult required before V2 ship (phishing-template surface) per §4.6 V2-ship-gate inventory item (i).
  • SD-01 Plaid account-share-decision data as credential-adjacent surface (RT-03). The user's Plaid Link account-share selections are tenant-scoped per §2.4.1 + RT-03. Account-share-decision data is medium-tier sensitivity (per §4.4 SD-01 row) — lower than the access token itself but adjacent to the credential surface because it records which institution accounts the user has authorized for Plaid-mediated read access. Newly-available-account detection on resync compares Plaid's current account list against this stored set; the "newly available — opt in?" prompt is the user-facing surface per §2.4.1.
  • No third-party security-master API calls at V1 — new-symbol metadata enrichment uses Plaid-only data. Per §2.4.1 verbatim. V1 does not call out to third-party security-master APIs that would expose user holdings to those providers; new-symbol enrichment uses provider-side data already delivered by Plaid for that holding. Any V2+ third-party security-master API integration requires separate Sec consult before ship (parallel posture to §4.6 V2-ship-gate inventory items (ii) / (iii)).
  • Spend-cap / API-quota alerting V2-implementation Sec-consult forward-pointer. Per §7.1 (a) origin + §4.6 V2-ship-gate inventory item (iv). If V1's ≤ $50/month cost target is operationalized as a runtime cost-protection control (auto-disable Plaid sync at threshold, alert at threshold, quota-tripped sync degradation), the implementation shape intersects the §2.4.4 re-auth flow's availability/phishing-surface tradeoff. Closes §7 routing flag (a) at §4 lock — flag lives forward at §4.6 V2-ship-gate inventory item (iv); §7.1 (a) reciprocation lands at §4 lock-time surgical edit per routing flag (m).

§4.3 Derivative-persistence and staleness posture

Two axes elevated at §2.6 lock — (v) staleness-live-read cross-tenant signal leak; (vi) snapshot store as derivative-persistence surface. β′ resolution from v1.30 verify-pass VP-2/12 applied at the RT-13 banner-name-string clause.

§4.3 lands V1's posture for two axes that §2.6 lock elevated as new Sec territory beyond the §2.1 → §2.5 isolation primitive: (v) staleness-live-read cross-tenant signal leak as a new verification surface, and (vi) snapshot store as derivative-persistence surface. The §4.4 matrix's tenant-scoped-derivative storage protection class exists specifically for axis vi (see §4.4 SD-12). §4.3 also lands the non-silent-staleness V1 commitment that anchors the §2.4.4 user-facing availability story per §4.6 availability posture.

  • Staleness-live-read cross-tenant signal leak (axis v — new Sec verification surface; RT-13). At §2.6.5 render time, every aggregation that consumed data from an account currently pending re-auth visually marks the stale-account contribution; the rendering layer joins from the §2.6.4 frozen snapshot's account_id to live §2.4.4 credential-error state per render. The cross-tenant signal-leak risk is that this live join must resolve under the requesting tenant's identity, not under any cross-tenant scope. Under a two-tenant fixture with overlapping account_id values (collision case), the staleness join must resolve to tenant A's credential state when rendering tenant A's snapshot, never to tenant B's. RT-13 verifies under both the in-app render path and the PDF re-render path; classified race-condition because the live-join-at-render-time pattern is concurrency-shape (multiple tenants may render simultaneously, the join must not race across tenant boundaries). The §2.6.5 banner additionally surfaces stale-contributing account-name strings inline; per §4.4's signal-correlation framing for identity-correlate name attributes (SD-01 / SD-11 canonical posture), account-name strings are protected as signal-correlation attributes, not as credential-class or financial-data-exposure classes. The banner's account-name string MUST resolve from the requesting tenant's SD-12 snapshot, not from any live join surface against §2.4.4 — Architect Phase 3 is constrained accordingly; the constraint is verified at RT-13. β′ resolution from v1.30 verify-pass VP-2/12 applied — High-severity per ADR-008 Decision 3; not critical because the failure-mode under the snapshot-sourced-name constraint is cross-tenant signal correlation (which-accounts-at-tenant-A-are-stale-leaks-behavior-to-tenant-B, including the account-name strings rendered as part of that signal), not cross-tenant credential or financial-data exposure.
  • Snapshot store as derivative-persistence surface (axis vi — SD-12). The §2.6.4 frozen-at-generation monthly-report snapshot denormalizes SD-00 baseline ledger + SD-04 bracket schedules + SD-05 tax_character categorization + SD-06 marginal-rate scalars + SD-07 Realized + Unrealized Tax Liability scalars + SD-08 aggregate G/L by tax_treatment + SD-09 est-payment ledger + SD-10 Rebalancing Targets commentary + SD-11 owner-identification trust-name + staleness-state into single rows per (tenant_id, target_month). The derivative inherits the storage protection class of the most-protected source class — per §4.4 SD-12 row, SD-12's storage protection class is tenant-scoped-derivative (a distinct enum value per ADR-008 Decision 2, specifically to flag derivative-of-multiple-classes posture). Retention is indefinite-with-V2-cold-storage-rollover per §2.6.4 χ-1; concrete cold-storage rollover mechanism is Architect Phase 3 per routing flag (f). RT-08 verifies cross-tenant snapshot store read isolation under three sub-tests (query by target_month / by report_id / via joined view).
  • Cross-cutting derivative-persistence axis (SD-13 cross-cutting annotation; applies forward to any future derivative-persistence surface). Per §4.4 SD-13 row + the cross-cutting cell-value convention. Any derivative-persistence surface that lands at V2+ (e.g., shared-link delivery from BACKLOG.md §5.6; pre-emptive notification surfaces from BACKLOG.md §5.4) inherits the same posture: storage-protection-class follows most-protected source class; retention-posture is independently Sec-flaggable; render-time-staleness-join must resolve under requesting-tenant identity. The axis is independently Sec-flaggable for retention-sprawl + blast-radius-widening + render-time-staleness-join compound risk — any V2+ derivative-persistence surface triggers Sec-consult at design time, parallel to §4.6 V2-ship-gate inventory item (iii).
  • Non-silent staleness as V1 commitment (the §2.4.4 user-facing availability story). Per §2.4.4 verbatim. Every aggregation that consumed data from an account currently pending re-auth visually marks the stale-account contribution — the §2.1.2 NAV trajectory, the §2.1.5 composition table, the §2.2.2 allocation table, the §2.3.2 cash-flow rollup, the §2.3.4 Historical Expenditures chart, and the §2.6 monthly report. Aggregations are never silently presented as fresh when constituent accounts are pending re-auth. This is the headline V1 product commitment of §2.4.4 and the V1 user-facing availability story per §4.6 availability posture — V1 doesn't commit to an uptime SLO; it commits to telling the user when data is stale, which is a stronger commitment than an SLO for the F/CTO's analytical use case. §2.6.5 staleness markers are derived from this commitment (per-section + report-banner naming stale accounts at render time per §2.6.5 lock).
  • Snapshot regeneration race condition preserves staleness-marker live-read coupling (RT-14). Per routing flag (i). Concurrent regenerations on same (tenant_id, target-month) produce exactly one snapshot row with last-writer-wins or transactional rejection (Architect Phase 3 picks the semantics); cross-tenant concurrency (tenant A regenerating month M while tenant B regenerating month M simultaneously) asserts no cross-tenant data mixing; regeneration does not silently rewrite the staleness layer — the staleness-marker live-read coupling at render path is preserved across regeneration. Classified race-condition and Related Class IDs SD-12, SD-13 because the race spans both the concrete snapshot store and the derivative-persistence axis.
  • PDF + cron worker tenant isolation as derivative-persistence-adjacent (RT-09 + RT-10). Background workers that generate or render snapshots establish tenant context before any source-data read or snapshot-store write (RT-09 cron worker tenant-context isolation); shared PDF worker pool does not leak fonts / DOM / auth headers / metadata across tenant renders (RT-10 PDF-generation worker tenant isolation). Both are worker-context-isolation test category per §4.5; both high-severity per ADR-008 Decision 3. Cron worker tenant-context-binding mechanism is Architect Phase 3 per routing flag (g); PDF worker isolation mechanism is Architect Phase 3 per routing flag (h).

§4.6 Cross-cutting posture commitments

Consolidation home for V1-locked posture commitments that don't belong to a single axis sub-section: data retention, availability/uptime, incident handling, parity-fixture handling, shadow-workflow tear-down, V2-ship-gate Sec-consult inventory. Closes ADR-002 §7.0 gaps #4 + #6 + partial-#5.

§4.6 is the consolidation home for the V1-locked posture commitments that don't belong to a single axis-grouped sub-section: data retention, availability/uptime, incident handling, parity-fixture handling, shadow-workflow tear-down, and the V2-ship-gate Sec-consult inventory. Each commitment closes one or more cross-section forward-pointers (closures enumerated at routing flags (m)–(p); see PRD Appendix B). §4.6 closes ADR-002 §7.0 missing-content gaps #4 (security and compliance posture as a whole — across all of §4) + #6 (offline / availability tolerance — at the availability bullet below) at V1 baseline and partially closes #5 (data retention — snapshot-side at §2.6.4 χ-1, non-snapshot at the retention bullet below) per routing flag (o).

  • Data retention (closes ADR-002 §7.0 gap #5 jointly with §2.6.4 χ-1). V1 retention posture is class-by-class per the §4.4 retention-posture column: indefinite retention on SD-00 baseline transactions/holdings/cost-basis ledger and on SD-04 through SD-11 high-tier and medium-tier non-credential classes (aligns with §2.6.4 χ-1 + the F/CTO's analytical use case; bounded retention would lose the §2.1.3 5-Year horizon depth); bounded-Item-active-only on SD-03 Plaid access tokens (server-side deletion on Item-deletion, not merely flagged-inactive; credentials are categorically deleted on the unbinding event, not retained "in case"); bounded-N-day-rolling with N = 90 days on SD-02 Plaid Item-state metadata (three monthly-report cycles of retrospective debuggability + headroom for delayed investigation, clearly under the 6+ month behavioral-correlate aggregation risk threshold; concrete prune mechanism is Architect Phase 3 per routing flag (e)); indefinite-with-V2-cold-storage-rollover on SD-12 monthly-report snapshot store (per §2.6.4 χ-1 lock) and on audit logs (V1 commits to indefinite at-V1 with V2 cold-storage rollover forward-compat; audit-log architecture itself is Architect Phase 3 per routing flag (f)). No user-facing delete-my-data control as a V1 surface — deferred to V2+ trajectory if the surface becomes warranted at the multi-user expansion per §7.3. Cross-reference §2.6.4 χ-1 — the snapshot-side retention commitment lives at §2.6.4 χ-1; §4.4 SD-12 row traces; §4.6 retention bullet consolidates the non-snapshot retention posture alongside it. Closes ADR-002 §7.0 gap #5 jointly with §2.6.4 χ-1 per routing flag (o).
  • Availability/uptime (closes ADR-002 §7.0 gap #6). V1 commits to best-effort uptime, no SLO. §7.3's single-user V1 deployment posture means "uptime" is what the F/CTO is willing to tolerate; committing to a numeric uptime target before Architect Phase 3 sizes the Coolify / VPS infrastructure would pre-judge Phase 3, and a numeric target in PRD scope conflicts with §7.1's per-line-item-out-of-PRD-scope boundary. The V1 user-facing availability story is the §2.4.4 non-silent-staleness commitment (per §4.3 above) — when data is stale because Plaid sync is degraded or because credential state requires re-auth, the user is told at every consuming surface; aggregations are never silently presented as fresh. This is a stronger commitment for the F/CTO's analytical use case than a numeric SLO: a numeric SLO commits to availability frequency but says nothing about data freshness when the system is technically up; the non-silent-staleness commitment guarantees that data freshness is visible regardless of system-uptime state. Architect Phase 3 sizes infrastructure-side uptime targets grounded in actual stack constraints without a PRD-locked numeric per §7.2 + §3 (a) routing. Closes ADR-002 §7.0 gap #6 per routing flag (o).
  • Incident handling (closes ADR-002 §7.0 gap #4 jointly with the rest of §4). V1 commits to an incident-log file at the F/CTO level as the V1 incident-handling primitive: when a security-relevant event surfaces (a failed RLS test in CI; a suspicious webhook signature failure pattern; a sync-error pattern that suggests credential compromise; a degraded-performance event that crosses the §7.2 scale dimensions), the F/CTO logs the event with timestamp, surface, observed behavior, and remediation taken. No on-call rotation, no severity rubric beyond the §4.5 three-tier (critical / high / medium), no postmortem template at single-user V1 — single-user-F/CTO incident response is what V1 ships; the conventional incident-response shape would be ceremony without value at this scale. V2-trajectory ramp to formal incident-response shape if/when the second user lands per §7.3 invite-only forward-compat: the V2-onboarding step adds (a) explicit incident-severity rubric (likely lifting the §4.5 three-tier as the rubric foundation), (b) postmortem template, (c) response-time targets, and (d) cross-user-incident-notification posture. V1 ships the incident-log primitive so the V2 ramp has a baseline data lineage; the V2 ramp design itself is V2-onboarding territory, not §4 V1 scope.
  • Parity-fixture handling (closes §3 (e) at §4 lock per routing flag (j)). Finance_Report_2026_04.pdf and the Asset Summary workbook are sensitive-data artifacts — they contain real F/CTO financial values across every account category — and are the canonical fixtures the §3.3 parity tests run against. V1 Sec posture: fixture artifacts are stored under access-controlled paths (specific access-control mechanism is Architect Phase 3 per routing flag (j) Architect/Sec joint); the CI test environment enforces tenant-scoping on fixture loads equivalent to production RLS (verified at RT-15); fixture-refresh cadence as the comparison month rolls forward is F/CTO-paced (the next parity-evidence month replaces the prior month's fixture under the same access-controlled storage; no historical fixture accumulation in CI). The §3 (e) Sec routing flag closes at this commitment + RT-15 verification + routing flag (j); the §3 (b) Architect/Sec joint test-environment plumbing flag closes at routing flag (j) per §3 (b) routing.
  • Shadow-workflow tear-down (closes §3 (d) at §4 lock). When the F/CTO retires the existing manual-spreadsheet system per §3.4(c) migration-completion criterion, the existing Google Sheet stops being a working data source — V1 commits to no dual-write to the existing Google Sheet after V1 lands. The historical NAV import from the existing system per §2.1 Architect routing flag terminates at V1 schema population — the import is a one-time event, not an ongoing sync. The F/CTO retains a read-only archive of the existing spreadsheets at a Sec-acknowledged access-controlled location (concrete location and access-control mechanism is F/CTO operational choice, not §4 V1 lock; what §4 commits to is the posture — the existing system exists post-V1 as a read-only audit reference, not as a working data source). A snapshot of the existing system's state at V1-final cutover is preserved as an audit artifact for the §3.4 migration-completion test verification path. Closes §3 (d) at §4 lock per routing flag (p). See also MILESTONE-FRAMING.md §8.2 drop-replace migration pattern for the user-continuity flip side of this commitment.
  • V2-ship-gate Sec-consult inventory (consolidates routing flag (k)'s four items). The following V2+ surfaces require Sec-consult before V2 ship per accumulated BACKLOG.md §5 + PRD §7 routing flags; the inventory consolidates them at one §4 anchor so V2-scoping work has a single reference point rather than scanning BACKLOG.md §5 / PRD §7 separately:
    • (i) Pre-emptive Plaid re-auth reminders (BACKLOG.md §5.4 origin). V1 ships reactive-only re-auth per §2.4.4; pre-emptive reminders introduce a phishing-template surface (an email or push notification that says "re-auth your bank here" is a phishing-template even when legitimate). Sec-consult at V2-design: notification channel, sender-identity verification, deep-link posture, user-side "is this real?" verification path.
    • (ii) Email/SMS report delivery (BACKLOG.md §5.6 origin). V1 ships in-app + PDF-export only per §2.6.3 + υ-1; email/SMS introduces a delivery-surface Sec-consult: payload sensitivity (the monthly report contains SD-07 + SD-10 + SD-11 + SD-12-derived content), delivery-channel encryption posture, recipient-verification posture, opt-in / opt-out controls.
    • (iii) Shared-link delivery to external viewers (BACKLOG.md §5.6 origin). V1 has no shared-link surface; V2+ trajectory would produce a derivative-persistence surface per SD-13 cross-cutting axis (the shared link is a delivered derivative of SD-12 snapshot content). Possible §6 advisor-axis re-litigation flagged at BACKLOG.md §5 lock — if the recipient set extends to fiduciary-implication external viewers, the surface re-tests against §6.3 advisor/fiduciary axis per ADR-007 (information-vs-prescription axis). Sec-consult at V2-design must address: SD-13 derivative-persistence posture for the shared-link artifact, recipient access-control mechanism, revocation posture, expiration posture, and the §6.3 axis test for the recipient set.
    • (iv) Spend-cap / API-quota alerting as cost-protection control (§7.1 (a) origin; V2-implementation). If V1's ≤ $50/month cost target is operationalized as a runtime cost-protection control, the implementation shape intersects the §2.4.4 re-auth flow's availability/phishing-surface tradeoff (a quota-tripped auto-disable on Plaid sync creates an availability-shaped failure mode). Sec-consult at V2-implementation must address: spend-cap mechanism shape (alert-only vs auto-disable vs degraded-sync), interaction with non-silent-staleness commitment (a quota-disabled account is a stale-data surface; how is that distinguished from a credential-error stale-data surface), and any user-facing surface the mechanism produces.

    Closes §7 routing flag (a) at §4 lock (the flag lives forward at item (iv) above); BACKLOG.md §5.4 + §5.6 V2-ship-gate flags remain V2-active but are inventoried here for V2-scoping reference per routing flag (k).
