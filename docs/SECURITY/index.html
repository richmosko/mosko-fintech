4. Security and compliance posture

§4 lands V1's security and compliance posture — the canonical reference layer for tenant isolation, credential handling, derivative-persistence + staleness, the sensitive-data classification matrix, the Phase 3 RLS test catalog, and the cross-cutting posture commitments (data retention, availability/uptime, incident handling). §4 is Security Reviewer primary-authored (first Sec primary-authorship in Phase 1 Step 3; prior Sec engagements were six at-lock pass-with-comments verdicts on PM-authored §2 sections). The canonical-reference layer is captured at ADR-008 with bullet-level posture commitments at §4.1–§4.6; ADR-008 establishes the immutability boundary for the six canonical Sec axes, the 14-entry sensitive-data classification matrix, the 15-entry RLS test catalog (both figures are the V1-lock snapshot; the catalog + matrix have since grown via their surface-introducing ADRs — now SD-23 / RT-28 per §4.4 / §4.5, indexed at the ADR-008 Phase-6 index amendment; the immutability discipline — structure/rubric/enums/amendment-rule — is unchanged), the V1 retention/availability/incident-handling baseline, and the two pattern divergences from PM-led drafting (hybrid format + two-stage drafting). §4 closes ADR-002 §7.0 missing-content gaps #4 + #6 + partial-#5; consumed by Phase 3 architecture work, Phase 5 migration design, Phase 6 PR review (Security Reviewer mandatory on every PR touching auth / data handling / external APIs / secrets / financial calculations), and Phase 7 incident handling.

§4.1 Tenant isolation posture

V1 isolation primitives — axes (i)–(iv) per ADR-008 Decision 1.

§4.1 anchors mosko-fintech V1's isolation primitive: tenant_id is the V1 isolation boundary; every other axis-of-parameterization on user-data query paths (scope, tax_treatment, date, account_id, target_month) is a data attribute or inclusion filter operating within the tenant boundary, not a parallel isolation boundary alongside it. This sub-section consolidates the four canonical Sec axes (i)–(iv) elevated through the six §2.x at-lock passes into V1-locked posture commitments per ADR-008 Decision 1. The §4.4 matrix's tenant-scoped, tenant-scoped-with-app-encryption, and tenant-scoped-derivative storage-protection-class values all assume the §4.1 isolation primitive as foundation (see §4.4); the §4.5 RLS test catalog's 14 active tests verify the posture commitments below either directly or as adjacent extensions (see §4.5).

  • tenant_id is the V1 isolation boundary (axis i — canonical clause). Every user-data table carries a tenant_id column; every read against a user-data table is enforced via Row-Level Security at the database policy layer to return only rows whose tenant_id matches the requesting tenant context. RLS enforcement is non-optional and is exercised (not bypassed) on the V1 single-user-tenant test path per ADR-002 §1.4 — single-user V1 is the deployment posture, not the isolation posture; the isolation posture is multi-tenant from day one. The 14 V1-mandatory tests in §4.5 verify this primitive across read paths, write paths, worker-context paths, and the test-environment posture; concrete RLS policy implementation is Architect Phase 3 per routing flag (a).
  • Multi-scope ownership is a tenant-scoped data attribute, NOT an isolation boundary (axis ii — canonical clause). The ownership-scope label set during account onboarding (e.g., personal, trust, retirement custodial, HSA) per ADR-004 Decision B is a scope column on user-data rows. Scope filtering happens at the application query layer above the RLS boundary — a tenant's query for "personal-scope NAV" runs as WHERE tenant_id = $1 AND scope = 'personal' where the tenant_id clause is RLS-enforced and the scope clause is application-layer-applied. V1 user-facing surfaces render full-household-only (per §2.1.7 / §5.1 per-scope deferral); the data model carries scope from V1 bootstrap so V2 per-scope rendering ships without a data migration. Scopes are user-owned data labels; tenant isolation is the isolation boundary.
  • tax_treatment is an inclusion-filter attribute, NOT an isolation boundary (axis iii — canonical clause). The three-way tax_treatment enum per ADR-002 §1.6 (taxable / tax-deferred / tax-free) on each account is a data attribute that filters which holdings contribute to specific aggregations (e.g., §2.5.4 Unrealized Tax Liability aggregates only tax_treatment IN ('taxable') per (π) lock). Like scope, tax_treatment filtering happens at the application query layer above the RLS boundary; tenant_id remains the isolation boundary across all tax_treatment filter combinations. The tri-axis query parameterization (tenant_id × scope × tax_treatment × date) verified at RT-06 is the canonical V1 query-shape envelope; future V2+ attributes that surface as additional inclusion filters operate within the same envelope and do NOT relax the isolation boundary.
  • Write-path RLS symmetry: write paths inherit the tenant-scoping the read paths enforce (axis iv — canonical clause). No write path in V1 bypasses the tenant-scoping the read path enforces. The four §2.4.x mutation paths (account onboarding, manual account creation, manual transaction entry / edit / split / skip / reconcile, re-auth completion) per §2.4.5 are tenant-scoped at the database policy layer; same applies to the §2.6.2 commentary write path (RT-11) and the §2.6.4 owner-identification settings-store write path (RT-12). Manual-entry write paths carry elevated integrity risk relative to Plaid-ingested data — a user can author a buy five years ago at any price, with direct impact on cost basis and downstream realized-G/L computation per §2.4.5 elevated-integrity posture. V1 acknowledges the asymmetry as a write-path-integrity concern distinct from but downstream-of the write-path-RLS commitment; the specific integrity mechanism is Architect Phase 3 territory routed through the §2.4 manual-entry write-path Architect/Sec joint flag.
  • Single-user V1 + multi-tenant infrastructure from day one (§7.3 cross-reference; closes §7.2 isolation-at-scale forward-pointer). Per ADR-002 §1.4 + §7.3 verbatim. The V1 usage model is explicitly single-user; the V1 isolation posture is multi-tenant. Isolation-at-scale posture per §7.2 forward-pointer (e) lands here: at V1 scale (single tenant) the §4.1 isolation primitive is exercised on every query under RLS; the scale-dimension question of how the isolation primitive holds at V2 multi-user scale (RLS query performance, cross-tenant query-plan stability, concurrent-tenant cron job isolation per RT-09) is Architect Phase 3 territory per §7.2 routing flag (b). §4.1 commits to the posture — RLS scale is first-class from day one even at single-user-V1 test paths; the implementation shapes are downstream. Closes §7 routing flag (e)'s isolation-at-scale forward-pointer at §4 lock.
  • account_trans read/write isolation exercises the V2 sharing-shape ACL at V1 (per ADR-011 Decision 7 / Lock 3 Option B; mod #4 advisory annotation; SELF-190 / migration 006). The pfin.account_trans RLS policies enforce read/write isolation via the account_users.rd_access-JOIN at SELECT and the account_users.wr_access-JOIN WITH CHECK at INSERT (mod #3) — the V2 multi-user sharing-shape ACL — even though V1 exposes no sharing or invitation UI. In V1 the JOIN resolves against a single creator-grant row per account (rd_access = wr_access = true, written by the SECURITY DEFINER fn_grant_creator_access trigger; authenticated holds SELECT-only on account_users per migration 003). V1 therefore exercises the V2 sharing ACL pattern in production against live financial data, so the V2 sharing-UI lands against an RLS pattern already proven — the F/CTO Option-B rationale at Lock 3. The cross-tenant re-tenant pivot Sec flagged load-bearing at Lock 3 (mod #1 column-level REVOKE UPDATE; GRANT UPDATE (nickname, notes) restriction) is inert in V1 because authenticated has no write path to account_users (SELECT-only grant + no INSERT/UPDATE/DELETE policy); mod #1 is hard-gated to the future PR that first grants such a write, per the 003 account_users table-comment hard-gate.

§4.2 Credential and external-API posture

V1 credential-class data class (SD-03 Plaid access tokens) + external-API surface (Plaid OAuth + webhooks). The two critical-severity tests (RT-02, RT-05) mark this boundary. Post-provider-generalization (ADR-027 / migration 015 linked_source fold), the credential class extends to SimpleFIN Access URLs under the same SD-03 Vault-handle storage discipline; the SimpleFIN revoke-residual bullet (C7) below captures the one posture divergence (no programmatic revoke endpoint).

§4.2 lands V1's posture for credential-class data and the external-API surface that introduces it. mosko-fintech V1 has exactly one credential-class data class — SD-03 Plaid access tokens — and exactly one external-API surface that handles credentials — the Plaid OAuth flow + webhook channel per §2.4.1 + §2.4.4. The asymmetry between credential-class data and the broader sensitive-data surface is intentional: credentials get categorically stricter handling than even high-tier financial-data classes because compromise yields direct unauthenticated access to a downstream system (the user's institution data via Plaid), not just exposure of stored financial state. The §4.5 catalog's two critical-severity tests (RT-02, RT-05) are V1-ship-blockers per ADR-008 Decision 3; the critical-severity tier exists at V1 specifically to mark the credential-class boundary.

  • Plaid OAuth flow integrity — credentials stay at the institution; mosko-fintech holds only a Plaid-mediated access token. Per §2.4.1 verbatim. The Plaid Link flow exchanges a short-TTL Link token → public token at the client → server-side /item/public_token/exchange for a long-lived access token; the institution credentials the user enters at the institution never touch mosko-fintech servers, and the access token never touches the client. Redirect URI is allowlist-bound. §4.2 reaffirms as V1 posture.
  • SD-03 Plaid access tokens carry credential-class storage protection (RT-02). Per §4.4 SD-03 row: the token is stored as a Supabase Vault secret (vault.secrets, Vault-managed authenticated encryption at rest) referenced by a uuid handle (access_token_secret_id) on pfin.plaid_items — the ciphertext never lives on the tenant row; decrypt is available only through the service_role-only pfin.decrypted_plaid_access_token view. Tenant-scoped non-negotiable, never client-facing. Retention is bounded-Item-active-only — server-side deletion on Item-deletion, not merely flagged-inactive: the referenced Vault secret is destroyed on Item removal (an AFTER DELETE backstop trigger on pfin.plaid_items covers every delete path, including user-deletion cascade, alongside the ordered revoke-then-delete in the /item/remove path). RT-02 verifies tenant isolation on the Plaid Item table where SD-03 + SD-02 co-locate; RT-02 is critical-severity per ADR-008 Decision 3 — Plaid Item table cross-tenant compromise is the V1-ship-block scenario. Mechanism note: the originally-locked shape (pgsodium column-level BYTEA + decrypt-view) was amended to this Vault-native secret-per-token mechanism at ADR-011 Decision 8 (Option-2 amendment, 2026-07-03 / SELF-196 / migration 007) — capability-driven (pgsodium non-viable on the pinned PG-17 stack); product behavior is identical except the retention lifecycle, which moves from cascade-by-construction to explicit secret cleanup. This supersedes the prior "concrete storage shape is Architect Phase 3" forward-pointer under routing flag (b).
  • SimpleFIN revoke residual — no programmatic revoke endpoint; local-delete-only, a documented product residual (C7 / ADR-027 amendment (dd)). SimpleFIN Access URLs are a second credential-class credential (SD-03-class), stored under the generalized Vault-handle discipline (vault.secrets ciphertext referenced by a uuid handle on pfin.linked_source, credential_secret_id withheld from authenticated; decrypt only via the service_role-only pfin.decrypted_source_credential view — the provider-agnostic generalization of the SD-03 Plaid pattern per migration 015). Unlike Plaid — whose /item/remove path carries an ordered revoke-then-delete with an abort-on-revoke-failure hard-gate — SimpleFIN exposes no programmatic revoke endpoint. SimpleFINAdapter.revoke() therefore performs the tenant-scoped local delete — destroying the stored Access URL in vault.secrets via the fn_linked_source_cleanup_vault_secret AFTER DELETE backstop (the generalized SD-03 retention trigger) — but the Access URL remains valid at the SimpleFIN Bridge until the user revokes it there. This is a documented product residual, not a code gap: the Plaid abort-on-revoke-failure hard-gate does not apply because there is no provider revoke call to fail. Sec-load-bearing consequence: because a compromised SimpleFIN Access URL cannot be programmatically killed by mosko-fintech, the never-log / never-client-readable credential discipline (Vault-handle-only storage, error-path scrubbing of both the Access URL and its Authorization header, no auth-bearing fragment on the client-readable provider_metadata column) is the sole line of defense at this surface — strictly load-bearing, not best-effort. The user-facing warning UX (surfacing "removing the connection here does not revoke access at SimpleFIN — revoke at the Bridge to fully terminate") defers to SELF-212 (C6).
  • Webhook signature verification gates production credential-state mutation (RT-05; hard Sec hard-line for V1 ship). Per routing flag (c). Every incoming Plaid webhook payload's signature is validated against the configured Plaid webhook signing secret before the payload routes to any credential-state mutation path; invalid-signature payloads are dropped with audit-log entry. RT-05 verifies under the adversarial-input battery (signature stripping, signature substitution from another Plaid app's secret, replay of valid-but-stale signatures, payload-body tampering with signature retained). Sec hard-line: V1 cannot ship with RT-05 failing or unimplemented. Routing flag (c) carries the Sec-sign-off-before-V1-ship requirement.
  • Four credential-error states handled non-silently (per §2.4.4 verbatim). The data model distinguishes at minimum (a) ITEM_LOGIN_REQUIRED (institution credentials invalid — user re-auths via Plaid Link); (b) INSTITUTION_DOWN (Plaid reaches the institution but it's offline — no user action required); (c) institution-side grant revoked (the institution withdrew Plaid's grant; user acts at the institution side); (d) user-side grant revoked at the institution (user revoked Plaid on the institution's portal; user re-authorizes there before re-auth here can complete). Finer UX presentation of (b) / (c) / (d) is Phase 2 territory; the data-model distinction holds in V1. Re-auth UX is in-session only — mosko-fintech sends no re-auth-link emails or SMS; institution credentials are entered only inside the authenticated app session, through Plaid Link itself. Pre-emptive Plaid re-auth reminders are V2+ per BACKLOG.md §5.4 with Sec-consult required before V2 ship (phishing-template surface) per §4.6 V2-ship-gate inventory item (i).
  • SD-01 Plaid account-share-decision data as credential-adjacent surface (RT-03). The user's Plaid Link account-share selections are tenant-scoped per §2.4.1 + RT-03. Account-share-decision data is medium-tier sensitivity (per §4.4 SD-01 row) — lower than the access token itself but adjacent to the credential surface because it records which institution accounts the user has authorized for Plaid-mediated read access. Newly-available-account detection on resync compares Plaid's current account list against this stored set; the "newly available — opt in?" prompt is the user-facing surface per §2.4.1.
  • No third-party security-master API calls at V1 — new-symbol metadata enrichment uses Plaid-only data. Per §2.4.1 verbatim. V1 does not call out to third-party security-master APIs that would expose user holdings to those providers; new-symbol enrichment uses provider-side data already delivered by Plaid for that holding. Any V2+ third-party security-master API integration requires separate Sec consult before ship (parallel posture to §4.6 V2-ship-gate inventory items (ii) / (iii)).
  • Spend-cap / API-quota alerting V2-implementation Sec-consult forward-pointer. Per §7.1 (a) origin + §4.6 V2-ship-gate inventory item (iv). If V1's ≤ $50/month cost target is operationalized as a runtime cost-protection control (auto-disable Plaid sync at threshold, alert at threshold, quota-tripped sync degradation), the implementation shape intersects the §2.4.4 re-auth flow's availability/phishing-surface tradeoff. Closes §7 routing flag (a) at §4 lock — flag lives forward at §4.6 V2-ship-gate inventory item (iv); §7.1 (a) reciprocation lands at §4 lock-time surgical edit per routing flag (m).
  • Webhook-bypass risk annotation (per ADR-011 Decision 8 / Lock 4 mod #5). The Plaid webhook handler is the canonical privileged-context-write surface (§6 meta-pattern origin per ADR-011 Decision 1): writes execute under service_role with no user JWT; tenant correctness derives from explicit code-derived users_id lookup at the Plaid Item ID; paired audit-log entry captures the tenant-resolution chain. Bypass risk: a forged webhook payload that defeats signature verification (RT-05 critical) AND somehow induces a tenant-resolution mismatch would write under service_role into the wrong tenant's scope. RT-05 closes the signature surface; Lock 4 mod #6 closes the tenant-resolution surface via the explicit `users_id` lookup pattern. The two together are the V1 V1-ship-block fence at this surface; failure of either is V1-ship-blocker per ADR-008 Decision 3 critical-severity rubric.
  • Plaid scheduled-poll annotation — third Plaid surface (per ADR-011 Decision 17 / Lock 13). V1's Plaid integration spans three external-API surfaces: (1) Plaid OAuth flow (V1 app TypeScript at §2.4.1 onboarding); (2) Plaid webhook (V1 app TypeScript at §2.4.4 handler — incoming-event reactive surface; covered at the webhook bullet above); (3) Plaid scheduled-poll worker (`pfin_back_etl` Python; fallback / catch-up to webhook; iterates per-tenant Plaid Items reading pfin.decrypted_plaid_access_token via the Vault-native service_role-only decrypt view per Lock 4 mod #1). All three share the pfin.decrypted_plaid_access_token service_role-only access pattern; scheduled-poll worker inherits Lock 13 mod #3 TenantBoundConnection discipline + mod #4 atomic audit-log into SD-19 pfin.plaid_sync_audit with source = 'scheduled_poll' discriminator. Cross-language audit-log discipline cohesion (webhook in TS + scheduled-poll in Python) closed via schema-as-contract at SD-19 per Lock 13 mod #8; drift impossible at data layer.
  • V2+ live tax-API ingestion forward-compat note (per ADR-011 Decision 18 / Lock 14 mod #8). PRD §2.5.2 V2+ list names "live tax-data API ingestion of bracket tables" as a future capability (IRS / California FTB public-published rate tables ingested + diffed; replaces F/CTO manual bracket maintenance). When that surface lands, it becomes a fourth privileged-context-write surface inheriting §6 discipline (Lock 11 mod #2 cron tenant-binding + Lock 13 TenantBoundConnection). Sec re-consult MANDATORY at adoption per Lock 14 mod #8 advisory fence — V2+ live-tax-API ingestion under service_role activates the cross-tenant FK-bypass family chain (per ADR-011 Decision 3) on pfin.tax_bracket_schedule.users_id column (which is V1-safe by-construction since V1 settings writes are user-session-bounded). At V2+ adoption, the Lock 12 mod #2 pattern (immutability DB-trigger fencing tenant-anchor `users_id` UPDATE post-creation) becomes V1-SHIP-BLOCK for that V2+ surface.
  • V1 web-app SUPABASE_SERVICE_ROLE_KEY allowlist CI grep fence (per ADR-011 Decision 4 §10 defense-in-depth meta-pattern second catalogued instance — RT-26). The V1 web-app server-side source surface — concrete file-glob enumeration locked in ARCH §4.1 at framework ratify — is fenced at CI grep time against any reference to SUPABASE_SERVICE_ROLE_KEY outside an explicit allowlist of legitimate service_role surfaces. Failure mode the fence catches: a developer (or Phase 6 AI coding agent) hits an RLS-enforced query failing under the authenticated tier, reaches for SUPABASE_SERVICE_ROLE_KEY as the "make it work" shortcut, and ships a server route that bypasses RLS by construction — silent cross-tenant data leak with no SQL-error signal at runtime. Allowlist-shaped (NOT wrapping-shaped) fence design: the fence enumerates permitted surfaces by file path rather than wrapping the env-var reference in a sanctioned helper — wrapping-shaped fences silently fail-open when a new server route lands under time pressure and reaches for the raw env var; allowlist-shaped fences fail-closed because any new reference outside the allowlist trips the grep at PR-time. Three-layer defense per §10 meta-pattern: code-layer (this allowlist CI grep fence on the V1-web-app server-side source surface) + JWT-shape-layer (RLS predicate users_id = auth.uid() bound under authenticated tier) + infrastructure-credential-presence-layer (Phase 3 ops bounds SUPABASE_SERVICE_ROLE_KEY runtime presence to allowlisted surfaces). All three layers required for defense-in-depth; failure of any layer is recoverable iff the other two hold. V1-SHIP-BLOCK posture obligation: V1 cannot ship with the allowlist CI grep fence absent or unenforced — parallel to the RT-05 Sec hard-line shape (HIGH severity + ship-block obligation; critical-severity reserved for credential-class admission boundaries per the §4.5 rubric). Webhook-allowlist annotation convention: the Plaid webhook handler is the canonical first allowlist entry (privileged-context-write surface per the webhook-bypass-risk bullet above + ADR-011 Decision 1); the Plaid /item/public_token/exchange server-side route is the canonical second allowlist entry (credential-class admission surface for SD-03 access tokens at first-onboarding-time per ARCH §7.1 endpoint 2; service_role posture inherits from the credential-class storage-class write-path stricture); the Plaid /item/remove server-side route is the canonical third allowlist entry (SD-03 retention enforcement surface anchoring bounded-Item-active-only per §4.6 + ARCH §7.1 endpoint 3; requires service_role to read pfin.decrypted_plaid_access_token per Lock 4 mod #1 before calling Plaid /item/remove); allowlist additions require Sec-consult + ADR amendment at the surface-introducing lock (the three V1 entries above are enumerated in ADR-016).
  • SELF-212 app→worker credential-admission channel (Option C internal HTTP; per ADR-027 amendment (hh) — RT-27). The Plaid onboarding relay resolves the app→worker handoff (ADR-027 (s) worker-owns-exchange) as an internal, private-Docker-network-only HTTP endpoint on the provider-sync worker — leg-1 link_token mint + leg-2 public_token exchange+admit — reachable only over the shared Coolify project network via the service name, never assigned a public Coolify Domain / never internet-exposed. Multi-layer defense-in-depth (Sec SC3-C6 conditions C6-1…C6-6 / CA-1…CA-6): (network-exposure) private-bind enforced by a worker startup fail-closed public-route env tripwire (pattern-matched, version-verified — CA-1) + a committed-Compose config-lint CI fence with both-vector golden fixtures (CA-5) + a deploy-time external-reachability negative smoke (CA-2); (auth) a WORKER_ADMISSION_SHARED_SECRET header, constant-time-compared + fail-closed, on BOTH legs — NOT SUPABASE_SERVICE_ROLE_KEY, so the RT-26 allowlist is UNCHANGED (the worker's service_role reach stays the direct-Postgres transport, off the code-layer allowlist); (tenant) ownerUserId derived exclusively from the server-validated session (auth.uid()) at the app relay, never browser-sourced, with the shipped fn_account_matched_linked_source (Decision-3 #6) as a downstream backstop — the in-code binding is the sole primary tenant-correctness control per ADR-027 (t); (atomicity) leg-2 is the one atomic service_role transaction with a post-exchange /item/remove recovery so a live, un-revocable Plaid Item is never orphaned; (logging) no public_token / access_token / secret / tenant-PII in either tier's logs or the error envelope (mirrors SELF-197 AC). Known post-deploy residual (Sec CA-2): a UI-added Domain after deploy combined with a Coolify stale-env bug (coollabsio/coolify #8912/#6124) can defeat the startup env tripwire — the deploy-time negative-reachability smoke is the load-bearing go/no-go backstop, and even under a tripwire fail-open the endpoint stays shared-secret-authed (authenticated-reachable, not open — a reduced-severity abuse/DoS residual, not an unauth breach; the multi-layer payoff). A recurring, @daily-poll-folded, /healthz-fingerprint external reachability probe (Discord-alerting, fail-safe) SHIPPED at SELF-279 — a recurring RUNTIME sub-limb of RT-27's existing network-exposure/config layer (limb (a)(iii)), runtime-complementing the existing deploy-time CA-2 smoke (deploy-smoke = go/no-go gate at deploy; recurring probe = drift-detector for a public Domain assigned AFTER deploy). Accepted residual (RF-3): an arbitrary custom (non-pattern) subdomain is not enumerable by an active probe — covered by the CA-1 boot tripwire's pattern-match + the CA-5 committed-Compose lint + PR review; even in that residual the endpoint stays shared-secret-authed (authenticated-reachable, not an unauth breach). Verified at RT-27. V1-SHIP-BLOCK posture obligation (parallel to the RT-05 / RT-26 hard-line shape).

§4.3 Derivative-persistence and staleness posture

Two axes elevated at §2.6 lock — (v) staleness-live-read cross-tenant signal leak; (vi) snapshot store as derivative-persistence surface. β′ resolution from v1.30 verify-pass VP-2/12 applied at the RT-13 banner-name-string clause.

§4.3 lands V1's posture for two axes that §2.6 lock elevated as new Sec territory beyond the §2.1 → §2.5 isolation primitive: (v) staleness-live-read cross-tenant signal leak as a new verification surface, and (vi) snapshot store as derivative-persistence surface. The §4.4 matrix's tenant-scoped-derivative storage protection class exists specifically for axis vi (see §4.4 SD-12). §4.3 also lands the non-silent-staleness V1 commitment that anchors the §2.4.4 user-facing availability story per §4.6 availability posture.

  • Staleness-live-read cross-tenant signal leak (axis v — new Sec verification surface; RT-13). At §2.6.5 render time, every aggregation that consumed data from an account currently pending re-auth visually marks the stale-account contribution; the rendering layer joins from the §2.6.4 frozen snapshot's account_id to live §2.4.4 credential-error state per render. The cross-tenant signal-leak risk is that this live join must resolve under the requesting tenant's identity, not under any cross-tenant scope. Under a two-tenant fixture with overlapping account_id values (collision case), the staleness join must resolve to tenant A's credential state when rendering tenant A's snapshot, never to tenant B's. RT-13 verifies under both the in-app render path and the PDF re-render path; classified race-condition because the live-join-at-render-time pattern is concurrency-shape (multiple tenants may render simultaneously, the join must not race across tenant boundaries). The §2.6.5 banner additionally surfaces stale-contributing account-name strings inline; per §4.4's signal-correlation framing for identity-correlate name attributes (SD-01 / SD-11 canonical posture), account-name strings are protected as signal-correlation attributes, not as credential-class or financial-data-exposure classes. The banner's account-name string MUST resolve from the requesting tenant's SD-12 snapshot, not from any live join surface against §2.4.4 — Architect Phase 3 is constrained accordingly; the constraint is verified at RT-13. β′ resolution from v1.30 verify-pass VP-2/12 applied — High-severity per ADR-008 Decision 3; not critical because the failure-mode under the snapshot-sourced-name constraint is cross-tenant signal correlation (which-accounts-at-tenant-A-are-stale-leaks-behavior-to-tenant-B, including the account-name strings rendered as part of that signal), not cross-tenant credential or financial-data exposure.
  • Snapshot store as derivative-persistence surface (axis vi — SD-12). The §2.6.4 frozen-at-generation monthly-report snapshot denormalizes SD-00 baseline ledger + SD-04 bracket schedules + SD-05 tax_character categorization + SD-06 marginal-rate scalars + SD-07 Realized + Unrealized Tax Liability scalars + SD-08 aggregate G/L by tax_treatment + SD-09 est-payment ledger + SD-10 Rebalancing Targets commentary + SD-11 owner-identification trust-name + staleness-state into single rows per (tenant_id, target_month). The derivative inherits the storage protection class of the most-protected source class — per §4.4 SD-12 row, SD-12's storage protection class is tenant-scoped-derivative (a distinct enum value per ADR-008 Decision 2, specifically to flag derivative-of-multiple-classes posture).
