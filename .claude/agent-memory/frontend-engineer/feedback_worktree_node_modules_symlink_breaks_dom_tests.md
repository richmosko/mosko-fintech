name: worktree-node-modules-symlink-breaks-dom-tests
description: Symlinking a fresh worktree's api/node_modules to the main checkout breaks every *.dom.test.ts suite; cp -a a real copy instead.
metadata:
  type: feedback
---

A fresh per-agent worktree has no `api/node_modules`. Symlinking it to the main checkout's
`api/node_modules` (the pattern already used by the `backend-engineer` worktree) makes `npm run
check` work fine but breaks EVERY `*.dom.test.ts` suite under `npm test` — including components
the branch never touched. `@testing-library/svelte/vite`'s `svelteTesting()` plugin resolves its
setup-file path (`@testing-library/svelte/src/vitest.js`) through Node's module resolution, which
follows the symlink to its REAL location outside the worktree root; Vite's dev-server then refuses
to serve that file (`Cannot find module '.../@fs/.../node_modules/@testing-library/svelte/src/vitest.js'`)
because it falls outside the project root's fs-allow list. The `node` vitest project (pure-TS /
SSR tests) is unaffected — only the `jsdom` project's `svelteTesting()` plugin hits this.

**Why:** discovered running SPEC A/B/Optional-C verification for SELF-356/357/360's close-out
follow-up (frontend-d worktree, 2026-09-07) — `npm test` reported 39 failed suites, all `*.dom.test.ts`,
including files the branch never edited, which is the tell that it's an environment artifact, not
a real regression. `npm run check` was clean throughout, which is consistent (svelte-check doesn't
route through Vite's dev-server fs.allow the same way).

**How to apply:** in a fresh worktree that needs `npm test` (not just `npm run check`) to exercise
DOM suites, do NOT symlink `api/node_modules` — instead `cp -a <main-checkout>/api/node_modules
<worktree>/api/node_modules` (APFS copy-on-write, near-instant, ~140MB). If a symlinked worktree
(e.g. `backend-engineer`) is later asked to run its own `*.dom.test.ts` suites, expect the same
failure and apply the same fix — don't spend time debugging the component code first.
