description: A worktree's node_modules symlinked to a sibling worktree can silently fail to collect some vitest suites (0 tests, not a failure count) — pass/fail alone hides this; check file counts too.
metadata:
  type: feedback
---

Some per-agent worktrees (e.g. `mosko-fintech-worktrees/backend/api/node_modules`) are a
symlink into a SIBLING worktree's real `node_modules` (e.g. frontend's), not a real install of
their own. Running `vitest run` there can produce a report that LOOKS clean — "0 failures" — while
several suites silently fail to *collect* at all (`Cannot find module '.../@fs/.../<pkg>/vitest.js'`
for a subpath-exports package like `@testing-library/svelte`), contributing 0 test cases instead
of their real count. The **file count still matches** what a healthy run would show (my run and a
clean run both said "98 test files") — only the composition differs: N "failed suites (0 test)"
vs N passed suites with real cases. Pass/fail totals alone don't surface this; compare file counts
AND look for `(0 test)` failed-suite entries.

**Root cause (diagnosed, not assumed):** cross-worktree symlink + Vite's `/@fs/` resolution of a
package's `exports` map subpath (`@testing-library/svelte`'s `./vitest` export) breaks when the
calling worktree isn't the one that owns the real `node_modules`. Confirmed by running the
identical test FROM the worktree that owns the real install — passes clean. Clearing the shared
`.vite` optimize-deps cache and `NODE_OPTIONS=--preserve-symlinks` did NOT fix it. Reproduces on a
clean base commit, unrelated to any in-flight diff.

**Why:** caught after a teammate (Architect) measured a real discrepancy between two "full suite,
0 failures" reports (938 vs 1014 passed) and refused to let "different trees" close it — that
explanation was falsifiable in one command (`git diff --name-only` between the two refs showed
zero test-file changes) and was wrong. The actual cause took several more steps to find. See
[[feedback_verifying_a_measurement_is_not_verifying_a_claim]] and
[[feedback_instrument_cannot_observe_the_property]] — a "0 failures" report is a claim about the
tests that RAN, not about the tests that were supposed to run, and a failed-to-collect suite is
invisible to a plain pass/fail scan.

**How to apply:** before reporting a vitest run as clean from any `*-worktrees/<agent>` path,
check whether `api/node_modules` is a real directory or a symlink (`ls -la` / `readlink`). If
symlinked to a sibling worktree, treat any "Failed Suites" section with `(0 test)` entries as a
collection failure, not a content failure — grep the affected files for any import touching the
surface under review before dismissing them as "unrelated," and say so explicitly rather than
folding them into a blanket "unrelated infra" line. This is per-worktree infra debt (routes to
DevOps if a fix is wanted — proper node_modules provisioning per worktree, not a symlink), not
something fixable from inside the role's Bash boundary (no `npm install` without confirmation).
